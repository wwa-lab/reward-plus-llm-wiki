# AS400 SME 快速上手指南

给熟悉 IBM i / AS400 和 BAU 业务的 SME 看。目标是让你知道：**Agent 能替你做什么、不能替你做什么、你的判断在哪一步最有价值、日常怎么开始。**

> 配套材料：[templates/sme-quick-guide.md](../templates/sme-quick-guide.md)（一页纸速查卡）和 [templates/sme-review-sheet.md](../templates/sme-review-sheet.md)（审阅表）。
> 本指南是 `NEEDS_REVIEW` 状态，流程还在试点阶段，遇到不一致以 [AGENTS.md](../AGENTS.md) 和 [CONTRIBUTING.md](../CONTRIBUTING.md) 为准。

## 0. 怎么读

- **30 分钟版**：第 1、3、4.1、6.A 节。
- **照着做的部分**：第 5 节（端到端流程）和第 6 节（日常场景）。
- **出问题时**：第 7 节。

## 1. 这个仓库现在是什么

- **是**：Reward Plus（信用卡积分系统，IBM i / AS400）的**知识仓库**，目标是为未来的 Java 迁移沉淀**可追溯**的知识：每条结论都能点回原文或扫描输出。
- **不是**：源码仓库。这里**不放源码**，只放经批准的扫描输出、业务文档、菜单导出、测试材料，以及整理后的知识页。
- **现状**：14 张登记表全部为空，还没有任何真实知识页。你的第一批输入会决定它长成什么样。
- **没有的东西**：没有自动摄取、没有扫描工具集成、没有数据库和 Web 界面，也不会自动提交。

## 2. Agent 的优势与劣势

| | 优势 | 劣势（必须警惕） |
|---|---|---|
| **阅读** | 一次读完整份清单或文档，不疲劳 | 超长文件会漏细节，应分批给 |
| **对照** | 文档、扫描、菜单三方两两比对很快 | 容易把"字面相似"当成"语义相同" |
| **检索** | 找出所有引用某程序、字段、规则的位置 | 只会在你给的范围内找，漏给的文件它不知道 |
| **格式** | 按模板、ID、状态输出，一致性好 | 给出的行号和程序名看起来很精确，但可能是错的 |
| **解释** | 能把代码和文档的逻辑组织成候选解释 | 不知道你们的隐性约定：指示器含义、日切时刻、人工补救习惯 |
| **版本** | 遵守规则时会标 `NEEDS_REVIEW` | 分不清哪份是现行版本，同名文件可能混用 |
| **执行** | 同一流程可以反复跑，结果可比较 | 不能访问生产，无法验证运行时行为 |

**一句话**：Agent 擅长"穷举地读、快速地对照、规范地记录"；不擅长"判断这在业务上对不对"。

## 3. SME 的优势与劣势

| | 优势 | 劣势 |
|---|---|---|
| **业务** | 知道业务为什么这样设计，哪些功能仍在用，哪些是历史遗留 | 记忆可能偏旧，或与同事的说法不一致 |
| **技术** | 知道指示器、参数、数据区的真实含义，知道作业的真实执行时刻和失败后怎么补救 | 口述不可追溯，需要转成依据才能入库 |
| **判断** | 一眼看出"结论看起来对但实际不合理" | 长时间逐条对照容易疲劳，容易漏看 |
| **信息** | 知道去哪找没写下来的东西，知道谁能裁决 | 对 AI 的结论容易过度信任，也容易一概否定 |
| **时间** | — | 时间最贵，应该用在判断上，而不是找文件和抄录上 |

**一句话**：你的价值是**判断**和**隐性知识**，Agent 的价值是**穷举**和**规范化**。两者互补，不要互相替代。

## 4. 分工：什么给 Agent，什么给你，怎么结合

### 4.1 任务分配

| 任务 | 主导 | Agent 做什么 | 你做什么 |
|---|---|---|---|
| 材料盘点、合规确认、归属 PRJ | 你 | 核对目录与文件清单，起草登记行 | 确认合规，判定归属 |
| 扫描结果：程序清单与职责 | Agent | 归纳职责草稿，列调用关系和数据访问 | 抽查 10–20%，判断职责对错 |
| 调用关系、数据访问的核对 | Agent | 全量对照，列出新增、一致、冲突、缺失 | 裁决冲突：哪一方是现行的 |
| 业务规则抽取 | 人 + Agent | 找规则候选，每条附来源 | 判断规则的业务含义、条件边界、例外 |
| 指示器、参数、数据区的语义 | 你 | 列出它们出现的位置，并提问 | 给出含义，口述时注明年份 |
| 功能描述、规范名与别名 | 你 | 汇总候选名称和出现位置 | 选定业务最常用的叫法 |
| 菜单映射 | 你 | 列出未匹配项，给出映射草稿 | 判断菜单与程序的对应关系 |
| 批量作业与执行时刻 | 你 | 从调度证据整理依赖 | 提供真实执行时刻、失败处理方式 |
| 测试用例整理 | Agent | 规范化用例，映射到规则 | 判断"预期结果"本身是否正确 |
| 冲突裁决、SME 确认 | 你 | 列出冲突和需要的裁决角色 | 明确回复"对"，由协调人记录你的名字和日期 |
| 影响分析 | Agent | 按"有直接证据 / 推断"两栏输出 | 补充业务影响：哪些人、哪些渠道会受影响 |
| git 提交 | 协调人 | 不做 | 协调人检查后提交 |

### 4.2 Agent 的能力边界

**Agent 不能做、也不应该做的事**：

- 替你裁决冲突，或标 `SME_CONFIRMED`。这只能由人标，并记录确认人和日期。
- 判断业务上"应该怎样"。期望行为来自你或文档，不来自读代码。
- 访问生产系统，或运行程序验证行为。
- 保证语义正确。它给出的证据位置可能是对的，但对位置的解释可能是错的。
- 知道你没给它的材料。它会声明覆盖范围，但不会自己补全。
- 完全理解复杂的 RPG / CL 控制流和指示器的隐含语义。这类地方要你来读。
- 处理超长的材料而不丢细节。材料应分批给。

### 4.3 人的能力边界

**人不适合做、应交给 Agent 的事**：

- 穷举对照几百上千条记录，容易漏。
- 保持同一术语在所有页面里的写法一致。
- 按模板机械地登记 ID、状态和证据引用。

**人的边界要靠流程补上的地方**：

- 口述不可追溯，记忆会"自动补全"。所以口述必须标注来源类型和年份。
- 一个人能深度审阅的量有限。所以每批控制在 10 条左右。

### 4.4 放大你能力的四种用法

1. **让 Agent 把扫描读成问题单。** 不要让它输出一份长报告，而是让它输出"这 8 个问题你能判断，请回答"。你的时间只花在判断上。
2. **把你的隐性知识写成提示笔记。** 例如"指示器 xx 在本系统里表示……"，连同年份和依据，放进 `analysis/reports/`。以后 Agent 每次分析时都会用到，而且会标注为口述。
3. **让 Agent 做全量对照，你只裁决冲突。** 扫描、文档、菜单两两对照的穷举工作交给 Agent，你只看它标出的 `CONFLICTED` 项。
4. **让 Agent 当第二双眼。** 你写下一条自己的判断，让 Agent 去找反例：有没有证据和这个判断矛盾？有没有你没考虑到的调用方？

## 5. 端到端流程（现阶段）

```text
S0 准备 ─▶ S1 入库 ─▶ S2 扫描分析 ─▶ S3 规则与术语 ─▶ S4 功能/菜单/作业/接口
                                                              │
S7 校验与提交 ◀─ S6 SME 审阅 ◀─ S5 测试与影响 ◀───────────────┘
```

| 阶段 | 对应流程 | 你（SME）做 | Agent 做 | 出口门禁 |
|---|---|---|---|---|
| **S0 准备** | W0 | 确认合规，确定本次范围（一个 PRJ，或一个程序群），指定协调人 | — | 合规已确认；PRJ 已登记（没有就由协调人登记） |
| **S1 入库** | W1 | 把材料放进 `raw/PRJ-####/<类型>/`，告知来源、日期、版本 | 核对目录和文件清单，起草 `SRC-` 登记行 | `raw/` 未改动；来源已登记；敏感内容不提交 |
| **S2 扫描分析** | W2 | 告知范围、优先程序、已知的版本和命名问题；抽查职责与调用关系 | 程序清单、职责、调用关系、数据访问；四张清单（新增 / 一致 / 冲突 / 缺失）；覆盖范围 | 每条结论有来源；覆盖范围写明 |
| **S3 规则与术语** | W3 | 对每条规则说明业务含义、条件、例外；给出术语的业务说法 | 规则候选（一条一规则），术语草稿，实现与期望的对照 | 单条规则；至少 1 处直接来源；冲突未抹掉 |
| **S4 功能 / 菜单 / 作业 / 接口** | W4–W7 | 定功能的规范名和别名，确认菜单映射，给出调度时刻和失败处理，说明对端系统 | 草稿页，未匹配菜单清单，映射置信度 | 映射有依据；没有一对一假设 |
| **S5 测试与影响** | W8–W9 | 判断预期结果是否正确，指出哪些功能对业务最关键 | 测试规格草稿，影响分析（两栏） | 测试通过不等于正确；覆盖范围写明 |
| **S6 审阅** | W10 | 用审阅表回复"对 / 不对 / 不确定" | 不参与此步 | 有具名确认人和日期才能标 `SME_CONFIRMED` |
| **S7 校验与提交** | 第 8–9 节 | 检查你负责的部分无敏感信息 | 可运行校验脚本，但不提交 | `python3 scripts/validate_repo.py` 无 ERROR；由协调人提交 |

### 5.1 一个审阅循环（每次 30–45 分钟，约 10 条）

1. **Agent 出审阅表**：按 [sme-review-sheet.md](../templates/sme-review-sheet.md) 的格式，每行是一条"我们的理解 + 原文依据"。
2. **你先点开依据看原文**，再判断。不要只看 Agent 的解释。
3. **在"你的判断"列填写**：对 / 不对 / 不确定。不对就写实际情况；不确定就写缺什么材料。口述要标注大概年份。
4. **协调人记录**：你回复"对"的，协调人记录你的名字和日期，并按 W10 更新状态。
5. **更新**：确认后的内容由 Agent 或协调人写入知识页；不确定的仍留在 `NEEDS_REVIEW`。

### 5.2 高效、高质的几条规则

- **一次只做一个 PRJ、一个程序群。** 不要把整批扫描一次喂完。
- **先做一次试点。** 挑一个你最熟的程序走完整条链路。试点既是校准，也是建立信任。
- **每批不超过 10 条，按迁移风险排序。** 高风险的先看，比如批量、对账、外部接口相关的。
- **口述要写清楚三件事：谁说的、什么时候、依据是什么。**
- **记下每一次"不对"的类型。** 类型比单个错误更有用，它会告诉协调人该改提示词，还是该补材料。
- **给 Agent 明确的范围和版本。** "这是 2019 年的规格"比"这是规格"有用得多。

## 6. Quick Start：日常场景

### 6.0 一次性准备

公司只批准 **OpenCode** 和 **GitHub Copilot**，以下步骤只针对这两者。

1. **确认前提：**
   - 你有有效的 GitHub Copilot 许可。
   - 公司 GitHub 组织允许 OpenCode 接入。如果被限制，需要管理员批准。
   - OpenCode 版本由 IT 统一安装。官方文档提示两代版本可能冲突，不要自己装另一个版本。
2. **在仓库根目录启动 OpenCode：**

   ```bash
   cd <仓库根目录>
   opencode
   ```

3. **连接 Copilot：** 在 OpenCode 里输入 `/connect`，选择 GitHub Copilot，然后在浏览器打开 github.com/login/device，输入终端里显示的验证码。用 `/models` 选择模型（以当前界面为准）。登录失败时，运行 `opencode auth list` 查看凭证是否已写入。
4. **验证规则是否生效（必做，不能跳过）：** 输入

   > 请先阅读 AGENTS.md，告诉我这个仓库的三条硬规则，并说明你读了哪个文件。

   - 能准确说出规则，并指出读了 `AGENTS.md`，才继续。
   - 说没读，或答不出来，就不要进入真实材料。之后每次会话开头都要显式要求它先读 `AGENTS.md`，并请协调人确认方案。
   - 背景：Copilot 下 OpenCode 曾忽略 `AGENTS.md`（[anomalyco/opencode #1130](https://github.com/anomalyco/opencode/issues/1130)），我们没有查到该问题已修复。
5. **不要运行 `/init`。** 官方文档说它会分析项目并创建 `AGENTS.md`。本仓库已有这个文件，运行它可能覆盖现有规则。
6. **确认材料可以进入：** 材料允许进入该仓库，并且你使用的工具已获批准可以处理内部材料。两者都要满足。
7. **确认 PRJ：** 查看 `knowledge/registry/projects.md`，找到对应的 `PRJ-####`。没有就告诉协调人登记。

> 只有 `/connect`、`/init`、`/undo`、`/redo` 来自官方文档。其他命令和按键以当前界面提示为准。Copilot 的登录步骤来自第三方教程，实际操作可能随版本变化。

### 6.A 按 project 导入文档与代码扫描结果（最常见）

**放置位置**（只放经批准的内容，且放进后不要修改文件）：

| 材料 | 放到 |
|---|---|
| 代码扫描结果 | `raw/PRJ-####/code-scan-results/` |
| 业务文档（PDF、Word 等） | `raw/PRJ-####/business-documents/`，文件名带版本和日期，例如 `xxx-spec-v3-2026-09.pdf` |
| 完整字段定义 | `raw/PRJ-####/data-dictionary/` |
| 不属于某次交付的（全量扫描、通用术语） | `raw/_shared/<类型>/`，不要随便放进一个 PRJ |

**然后：**

1. 复制 [templates/manifest-template.md](../templates/manifest-template.md) 为 `raw/PRJ-####/_MANIFEST.md`，记录来源、提供方、日期、版本、范围、导出方式和 LAN 位置。代码扫描结果还要记录 commit SHA。
2. 对 Agent 说（把占位符替换成实际值）：

   > 请按 W1–W3 处理 `raw/PRJ-####/code-scan-results/<文件名>`，所属交付 `PRJ-####`。先在 `analysis/reports/` 里查找适用的旧报告，有就续写。输出程序清单、职责、调用关系、数据访问、规则候选。每条结论标注 `EVIDENCE_FOUND` / `INFERRED` / `NEEDS_REVIEW`，并给出来源位置。写明覆盖范围。

3. 收到结果后：先看**覆盖范围**和**未覆盖项**；抽查 10 条的依据，逐条点开原文；把你判断不了的整理成审阅表。
4. 交给协调人入库和校验。

### 6.B 按 feature（PRJ）导入配置文件和相关文档

配置文件放在 `raw/PRJ-####/control-files/`。**这类文件默认不提交到 Git。** 要提交，必须由协调人显式加入并完成脱敏评审。

**注意**：不要把配置文件里的真实值粘贴到聊天框里。让 Agent 直接读本地文件，并且只在已批准的工具中处理。

对 Agent 说：

> 请分析 `raw/PRJ-####/control-files/<文件>` 和 `raw/PRJ-####/business-documents/<文件>`。判断每个参数是**真配置**还是**业务数据表**（判据：谁在改、多久改一次）。真配置写 `CFG-` 草稿：参数语义、取值域（**不写生产值**）、读取它的程序位置、改它会影响什么。硬编码常量也要找出来。判断不了的标 `NEEDS_REVIEW`，并说明需要谁判定。

**你要补的内容**：每个参数在业务上是什么意思、什么时候会改、改了会影响谁。这是 Agent 无法从代码里读出来的。

### 6.C 菜单导出

放到 `raw/PRJ-####/fe-menus/`。对 Agent 说：

> 请梳理 `raw/PRJ-####/fe-menus/<文件>` 的菜单层级，列出 `MENU-` 候选。映射到功能或程序，只在有证据时填写，并给出映射置信度。输出"未匹配菜单项"清单。

**注意**：一个菜单可能触发一串程序，一个程序也可能被多个菜单调用。不要假设一对一。

### 6.D 测试用例与测试结果

- 测试定义放 `raw/PRJ-####/test-cases/`，执行结果放 `raw/PRJ-####/test-results/`，两者分开。
- 对 Agent 说：

  > 请抽取 `raw/PRJ-####/test-cases/<文件>` 的业务场景、前置条件、输入、步骤和预期结果，关联到 `FUNC-` / `PROG-` / `RULE-`。列出没有任何测试覆盖的规则。

- **只有 `test-results/` 里有原始输出，才能写"通过"。** 测试通过也不等于业务正确，它只说明"这个输入下得到这个输出"。

### 6.E 影响分析

对 Agent 说（ID 需要已登记才能用）：

> 请对 `RULE-####` 做影响分析。分两栏输出："有直接证据的依赖"和"推断的依赖"。列出可能受影响的接口、测试、菜单、批量作业、控制参数（`CFG-`）和外部系统（`SYS-`）。写明证据缺口和覆盖范围。

### 6.F 日常常用的提问方式

| 你想做的事 | 可以这样说 |
|---|---|
| 看一个程序的职责 | "请从扫描结果里整理 `PROG-####` 的职责、调用方和被调方，附来源。" |
| 核对规则 | "请对照文档和扫描，检查 `RULE-####` 的条件和结果是否一致；不一致的标 `CONFLICTED`。" |
| 找缺口 | "请列出这个 PRJ 里还没有业务映射的程序和菜单项。" |
| 准备审阅 | "请按 sme-review-sheet 的格式，把本次需要我判断的内容整理成 10 条以内的审阅表。" |
| 看上次的进展 | "请查看 `analysis/reports/` 里关于 `PRJ-####` 的报告，列出未解决的缺口。" |

## 7. 常见问题与纠正

| 现象 | 怎么办 |
|---|---|
| Agent 给了行号，但你点开对不上 | 退回，要求重新定位。把它记为一次"来源错误"。 |
| 结论没有来源 | 要求补来源。补不上就降为 `INFERRED` 或 `NEEDS_REVIEW`，或移到 `analysis/`。 |
| Agent 写了"SME 已确认" | 无效。只有你明确回复"对"，并由协调人记录你的名字和日期，才算确认。 |
| 你的口述被写成了"原文" | 指出来，要求改回口述，并标注年份。 |
| 材料归属不确定 | 写"待判定"，不要随便选一个 PRJ。 |
| 材料里有真实卡号、客户信息或生产值 | 停止，不要粘贴到对话里，立即告知协调人。 |

## 8. 术语速查

| 术语 | 含义 |
|---|---|
| **PRJ-####** | 一次遗留交付（某年为某个 feature 做的改动），是材料的组织单元和迁移的批次单元 |
| **FUNC-####** | 业务功能，业务语言描述，例如"每日积分累积" |
| **PROG-####** | 程序，例如 RPG 或 CL 程序 |
| **RULE-####** | 业务规则，一个条件加一个结果 |
| **DATA-####** | 数据实体，文件或表 |
| **CFG-####** | 控制参数，改它会改变系统行为 |
| **JOB-####** | 批量作业（作业流），程序本身用 PROG- |
| **MENU-####** | 菜单项 |
| **IF-####** | 与外部系统的接口（内部程序调用不建 IF） |
| **SYS-####** | 外部对端系统 |
| **TERM-####** | 业务术语，用于消歧 |
| **EVIDENCE_FOUND** | 有直接证据 |
| **INFERRED** | 推理得出，未直接验证 |
| **NEEDS_REVIEW** | 证据不足，需要人评审 |
| **SME_CONFIRMED** | 具名专家明确确认过（只能人标，必须有名字和日期） |
| **CONFLICTED** | 来源相互矛盾，两方都保留，等人裁决 |
| **SUPERSEDED** | 已被取代，保留原文并指向新条目 |
