# 工作流细则

README 里写的是"场景"，这一页写的是"步骤 + 准入门槛"。

**当前全部为手动流程。** 没有自动摄取、没有解析流水线、没有扫描 Skill 集成。流程靠人 + Agent 一步一步走。

每个工作流末尾有**门禁**，不满足就不能往下走。门禁不过 → 停在当前层，报告缺口。

---

## W0 — 上手

1. 读 [README.md](../README.md)（尤其 7.5 状态规则、7.9 提示词）。
2. 读 [CONTRIBUTING.md](../CONTRIBUTING.md)（ID、命名、证据格式）。
3. 读 [AGENTS.md](../AGENTS.md) 与 [agents/README.md](../agents/README.md)。
4. 看 `knowledge/registry/` 各表，了解已登记了什么、哪些是 `NEEDS_REVIEW`。
5. 看 `analysis/reports/` 有没有半成品。

**门禁**：能回答——已登记哪些实体、哪些待评审、哪些卡在 SME。

---

## W1 — 导入原始材料

1. **先确认合规**：这份材料允许进这个仓库吗？（公司数据处理政策）
2. **先定 project。** 这份材料属于哪一次交付？查 `knowledge/registry/projects.md`：
   已有对应 `PRJ-####` 就直接用；没有就先登记一行（`PRJ-####` + 名称 + 年份 + 改动类型）。
   确实跨 project 或全局的（全量扫描、通用术语表、平台级配置）→ 归 `raw/_shared/`，
   并在 manifest 里写明"归属待定"的理由。**不要因为不确定就随便塞进一个 project**——归属错了比不归属更糟。
3. 放进 `raw/PRJ-####/<类型>/`，文件名带版本/日期。**只建用到的类型子目录，不预建空的。**
   类型规则见 `raw/_types/`。**完整字段定义导出放 `data-dictionary/` 类型目录**（不进 `knowledge/`）。
4. 每个 project 目录一份 `_MANIFEST.md`：收到什么、谁给的、什么时候、版本/范围、导出方式、LAN 来源。
5. 登记 `SRC-0001` 到 `knowledge/registry/source-materials.md`，写清 `SRC-####` ↔ LAN 路径 ↔ 所属 `PRJ-####`。
   **材料没进库时，这份登记就是唯一的线索。**
6. **不修改、不转换、不"整理"**。需要可读副本 → 放 `analysis/`。
7. 若材料含源码片段 / 凭证 / 個人资料 / 生產数据 → **不提交**，标记待评审。

**门禁**：文件在正确的 project 目录（或 `_shared/`）；`git status` 里 `raw/` 无修改；无敏感内容；
有 `_MANIFEST.md`；已登记 `SRC-`，且 `SRC-` 的 `PRJ-` 归属明确。

---

## W2 — 分析代码扫描结果

1. 只在 `raw/PRJ-####/code-scan-results/` 里放**经批准**的扫描输出。
2. 按[任务内核验规则 §10.0](evidence-and-validation.md#100-默认执行顺序与维护责任)先找并续写适用的分析报告；没有才新建。
   内容包括程序清单与职责、调用关系、数据访问、可作为规则证据的代码位置；保留已有缺口及动作历史。
3. 若扫描输出含**完整字段定义** → 存 `raw/PRJ-####/data-dictionary/` 并登记 `SRC-####`；
   `DATA-####` 页用 `dictionary_ref` 引用它，**只写驱动行为的字段，不抄字段清单**。
4. 若扫描输出暴露**控制文件 / 参数文件**（程序读取的参数表、数据区、硬编码常量）→ 登记 `CFG-####`。
   **先判定真配置还是业务数据表**（判据：谁在改它、多久改一次）；真配置要写**反向映射**。
   实际值放 `raw/PRJ-####/control-files/`（敏感，默认不提交）。
5. 与已有 `PROG-` / `FUNC-` 对照，输出四张清单：新增 / 一致 / 冲突 / 缺失映射。
6. 冲突进"冲突"段落，标 `CONFLICTED`，说明谁能裁决。
7. 写清**覆盖范围**（扫了多少、分析了多少、哪些没分析）。
8. 评审通过后，才创建/更新 `knowledge/programs/PROG-####-*.md`。
9. **不把完整源码拷进知识页**，只引用扫描输出路径 + 位置。

**交付前核验（在第 8 步评审前完成）**：按[任务内核验规则](evidence-and-validation.md#10-w2w3-的任务内核验)
读取已有核验记录并重新枚举本次材料范围；双向检查程序身份、调用方向、数据访问、规则候选及副作用。
有明确证据的错误在草稿中直接修正并复核；缺口按共同补证动作合并，未变化的已提动作不重复询问。
四张清单照常保留；空清单写“无”，未覆盖写明。结果附在同一份分析报告中，列出复用依据和剩余阻塞。

**门禁**：ID 已登记；模板段落齐全；每条结论有来源；冲突已记录未抹掉；覆盖范围已写明；状态未超过 `NEEDS_REVIEW`（除非 SME 已确认）。

---

## W3 — 抽取业务规则

开始前执行[任务内核验规则 §10.0](evidence-and-validation.md#100-默认执行顺序与维护责任)；从 W2 继续时沿用原报告，独立开始时先检索已有报告与缺口。

1. **先做术语消歧。** 这条规则里出现的业务词，去 `registry/terms.md` 查；没有就登记 `TERM-####`，
   并指向相关的 `DATA-` / `FUNC-`。**用词不一致是规则被理解错的头号原因。**
2. 确认这是**一条**可独立识别的规则（一组共同生效的条件 + 一个结果）。仅在结果和适用条件能独立成立时拆分；不要因出现“并且”就拆散联合前提。
3. 查 `registry/business-rules.md` 是否已存在或已有别名。
4. 分配 `RULE-####`，用 `templates/business-rule-template.md` 写。
5. 区分**已实现行为**（代码证据）与**期望行为**（文档证据）；两者不同就在"冲突"段落写清。
6. 只靠推断 → 状态 `INFERRED`，不得标 `EVIDENCE_FOUND`。

**交付前核验**：按同一[任务内核验规则](evidence-and-validation.md#10-w2w3-的任务内核验)，
检查适用版本、条件、结果、计算粒度、单位、边界与例外。拆分规则时保留共同前提，
不能把联合条件拆成各自独立生效的规则。明确证据支持的误读和遗漏直接修正；
期望与实现不一致时保留双方。报告或提议 diff 核验后进入现有人工评审，核验不授权提前写入权威层。

**门禁**：单条规则；至少 1 处直接来源；已关联实现它的 `PROG-`；术语已消歧或已标 `NEEDS_REVIEW`；冲突已记录。

---

## W4 — 描述业务功能

1. 用**业务语言**描述。如果必须提到程序名才能说清楚，说明还没理解透，回到 W2。
2. 查重、分配 `FUNC-####`，用 `templates/function-template.md`。
3. 填写触发方式、输入输出、主流程、相关程序、规则、数据、接口、菜单、批量作业、测试。
4. 双向维护关系（功能页列 `PROG-0003`，程序页也列 `FUNC-0001`）。

**门禁**：业务级描述成立；至少 1 个实现程序 + 1 份业务描述或 SME 说明；所有引用 ID 都能在登记表里查到。

---

## W5 — 菜单与导航映射

1. 从 `raw/PRJ-####/fe-menus/` 的导出梳理菜单层级，登记 `MENU-####`。
2. 映射到功能/程序时**必须有证据**：调用链、程序名与菜单标签的对应、或 SME 说明。
3. 没有证据的映射 → `INFERRED` 或 `NEEDS_REVIEW`，并在"待解问题"写明需要什么证据。
4. **不要假设菜单项与程序一对一。**
5. 输出"未匹配菜单项"清单——这是很有价值的缺口报告。
6. 映射置信度单独一列记（`mapping_confidence`）。

**门禁**：每个映射都标了置信度与依据；未匹配项已列出；无一对一的隐含假设。

---

## W6 — 批量作业梳理

1. 从作业清单/调度证据登记 `JOB-####`。批量**程序**仍用 `PROG-`。
2. 记录：调度周期、前置依赖、执行顺序、输入输出、下游影响、失败处理。
3. 关联到涉及的 `FUNC-` / `PROG-` / `DATA-` / `IF-`。

**门禁**：有调度或调用链证据；依赖关系分"有证据"和"推断"两栏写。

---

## W7 — 接口与外部系统梳理

1. 先按 [data-and-interfaces 的边界规则](../knowledge/data-and-interfaces/README.md) 判断**该不该建 `IF-`**：
   内部程序调用 → 记在 `PROG-` 页的 callers/callees；用户菜单与屏幕 → 走 `MENU-`；
   **只有与外部系统的交换才建 `IF-`**。
2. 登记对端系统 `SYS-####`（职责、协议、对接方），来源可为接口规格文档、扫描输出、调度证据。
3. 登记 `IF-####`：方向、类型（文件 / 数据队列(DTAQ) / 消息队列(MQ) / API / 数据库直连 /
   远程程序调用 / 屏幕终端 / 打印与假脱机 / 共享文件）、对端 `SYS-`、生产方与消费方 `PROG-`、触发与执行模式。
4. 字段映射指回 `DATA-####`，**不复制字段定义**。
5. 错误处理逐项写：校验失败、拒绝、重试、重复处理、错误通知。
6. 批量文件交换：物理结构归 `DATA-`，交换契约归 `IF-`。
7. **不登记凭证、连接串、账号、生产地址**；对端名称若敏感，用代号并注明原因。

**门禁**：每条接口有对端 `SYS-` 或明确标注"无对端（内部）"；字段映射指回 `DATA-`；无凭证类内容。

---

## W8 — 测试与验证

1. 测试定义进 `raw/PRJ-####/test-cases/`，执行结果进 `raw/PRJ-####/test-results/`。
2. 登记 `TEST-####`，用 `templates/test-case-template.md` 写规格。
3. 关联到 `FUNC-` / `PROG-` / `RULE-`。
4. 执行后把原始输出放进 `raw/PRJ-####/test-results/`，在 `TEST-` 页引用它，**没有引用就不能写"通过"**。
5. 失败或意外结果 → 记为发现，可能推翻已确认知识；上报，不要改期望值让它变绿。
6. 用例数据一律合成或掩码，**禁止真实卡号/客户信息**。

**门禁**：期望结果先于执行定义；原始结果已存并引用；失败已记录为发现；无敏感数据。

---

## W9 — 影响分析

1. 确定目标实体（功能/规则/程序/数据实体/接口/外部系统）及其 ID。
2. 沿登记表和知识页记录的关系追踪。
3. **分两栏输出**：有直接证据的依赖关系 / 推断出来的依赖关系。
4. 列出可能受影响的接口、测试、菜单、批量作业、下游功能、**控制参数 `CFG-`**，
   以及**需要通知的外部系统 `SYS-`**。
5. 明确写出**证据缺口与覆盖不完整**之处。
6. 涉及"这个功能被哪些交付改过"时，用**功能 × project 矩阵**（行 = `FUNC-`，列 = `PRJ-`）：
   行密度高 = 被反复改动 = 迁移风险高；一列 = 一次交付的改动范围 = 分批迁移的天然边界。
7. 报告放 `analysis/reports/`。

**门禁**：两类依赖分开；覆盖范围写明；缺口已列出；结论不暗示"已完整"。

---

## W10 — 评审与晋升

1. 评审者检查：每条结论有来源？事实/推断分开？冲突保留了？ID 已登记且无重复？`raw/` 未被修改？
2. 获得具名专家明确确认后，由人将状态改为 `SME_CONFIRMED` 并填 `reviewed_by` / `reviewed_at`。
   Agent 自检、结构校验、材料核对及核验复用均不等同于专家确认。
3. 不通过 → 退回 `NEEDS_REVIEW`，写明缺什么。
4. 被取代 → 标 `SUPERSEDED` + `superseded_by`，保留原文。
5. **Agent 不执行本步骤。**

评审入口附上修正后的候选、必要的前后差异、核验记录和合并后的重大缺口。
评审绑定实际输入与候选版本；相关内容改变后重新检查受影响部分。
事实错误及关键遗漏必须修正，核心冲突或必要证据缺失的部分留在分析层。
合并和不重复询问不免除这些门禁，不把等待裁决记成已通过。

**门禁**：记录了具名的人；全仓不存在无确认人的 `SME_CONFIRMED`。

## 变更报告模板

每次任务结束时填写：

```markdown
## 变更
- 新增：<路径>
- 修改：<路径>
- 登记 ID：<ID 列表>

## 证据状态
- NEEDS_REVIEW：<ID> —— 缺什么
- INFERRED：<ID> —— 推理依据
- CONFLICTED：<ID> —— 冲突双方 + 谁能裁决

## 覆盖范围
分析了 <X> 个中的 <Y> 个；未覆盖：<Z>

## 核验摘要（W2/W3）
- 自动修正：<问题及来源，或无>
- 复用／重查：<原记录、输入与候选快照、判断依据>
- 核验方式：<Agent 自检／实际独立核对者；未核验范围>
- 合并缺口及当前阻塞：<本次需采取的动作；已提且未变化的动作不重复询问>
- 详细记录：<同一分析报告中的位置，使用 analysis/reports/README.md 模板>

## 假设
- <假设及理由>

## 因证据不足而未做的事
- <事项>

## 下一步最小动作
- <一个具体动作>
```

## 建议的推进顺序

**先跑通一条完整链路**（W1 → W2 → W3，一个程序端到端），再谈批量。一条完整链路能把这套约定里所有硌脚的地方暴露出来，成本远低于分析二十个程序之后再返工。

批量阶段**按 `PRJ-` 分批**，而不是按目录或字母顺序：一次交付的改动范围本身就是一个可独立验证、可独立回退的迁移单元。先做那些"只被一个 `PRJ-` 碰过、且碰得浅"的功能。
