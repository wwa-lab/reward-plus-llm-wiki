# 证据与验证模型

## 1. 什么是证据

证据 = 一个**人能打开并核对**的指针，指向仓库里的材料。没有证据的结论只是意见，只能放 `analysis/`。

### 引用格式

```markdown
- 来源：`raw/PRJ-0001/code-scan-results/program-inventory-2026-09.csv`，行 142 —— 程序清单
- 来源：`raw/PRJ-0001/business-documents/points-spec-v3.pdf`，第 14 页 —— 兑换规则章节
- 来源：`raw/PRJ-0001/test-cases/redemption-cases.xlsx`，工作表 Cases，第 42 行
- 来源：`raw/PRJ-0001/test-results/run-2026-09-30.log`，行 880-915
- 来源：`raw/_shared/fe-menus/menu-export-2026-08.xlsx`，工作表 MENU —— 跨 project 的通用导出
- 来源：`knowledge/programs/PROG-0003-XXX.md` —— **派生**页面，仅代表先前分析结论
```

`raw/` 下材料的路径形态是 `raw/PRJ-####/<类型>/<文件>`；跨 project 的通用材料写成
`raw/_shared/<类型>/<文件>`。**引用里必须带 `PRJ-####` 或 `_shared`**——只写 `raw/<类型>/` 无法定位到具体一批材料。

可用的定位键：行号（`行 120-168`）、页码、工作表 + 行号、程序名、用例编号、章节。

**能拿多细就写多细；拿不到就写"位置未知"。** 编造行号比不写行号危害大得多。

引用派生页面（知识页）时必须注明"派生"——它是**先前分析的证据**，不是系统行为的证据。

### 引用写在哪：两处都写，各有用途

| 位置 | 形态 | 谁在读 | 校验 |
|---|---|---|---|
| front matter 的 `source_refs` | 路径列表（YAML） | 机器 | `scripts/validate_repo.py` **会检查路径是否存在** |
| 正文的"证据与来源引用"段 | 代码路径 + 定位键 | 人 | 不校验（但 markdown 链接形态会被查） |

两处都要写。只写正文 → 机器查不到，路径写错无人发现；只写 front matter → 人翻页时看不到这条证据支持了什么。

**演练教训（2026-10-10）**：最初只校验 markdown 链接，于是 front matter 里的 `source_refs` 路径写错、
正文写成代码路径的证据全部**静默通过**。现在 `source_refs` 的路径存在性会被校验。

### 引用"默认不提交"的材料

配置快照（`raw/*/control-files/`）按约定默认不进版本库。引用它们时：

* **照常写路径**，校验脚本会对这一类路径豁免存在性检查（只记 INFO，不报错）。
* 在正文里**注明**"配置快照，默认未提交"，让 clone 仓库的人知道为什么打不开。
* 仍然要在 `knowledge/registry/source-materials.md` 登记 `SRC-####`（含 LAN 路径）——
  否则这份材料在仓库里就彻底失去线索了。

## 2. 证据强度

| 强度 | 类型 | 说明 |
|---|---|---|
| 1（最强） | 测试执行结果 | 系统实际跑出来的行为 |
| 2 | 代码扫描结果 | 程序实际实现的逻辑 |
| 3 | 系统运行观察（屏幕、作业日志） | 看到的行为，未必能从代码复现 |
| 4 | 正式规格 / 设计文档 | 期望行为，**前提是版本是最新的** |
| 5 | 叙述性文档、手册、邮件 | 意图，通常偏旧 |
| 6 | 流程图、架构图 | 结构信息，规则层面通常不精确 |
| 7 | 由命名 / 结构推断 | 仅提示性 |
| 8（最弱） | Agent 推断 | 必须显式标为推断 |

两条推论：

* **版本优先于类型。** 五年前的规格书打不过今天的代码，但也不能自动判代码赢——记录版本差异并标 `CONFLICTED`。
* **已实现 ≠ 期望。** 代码说明"实际会发生什么"，不说明"业务想要什么"。这个落差正是 `NEEDS_REVIEW` 存在的理由。

## 3. 状态与可信度

六个状态见 [knowledge-model.md](knowledge-model.md) §5。补充字段 `confidence`（`high`/`medium`/`low`/`unknown`）表达**解释**的可信程度，与状态互不替代：

* `EVIDENCE_FOUND` + `confidence: low` —— 有直接证据，但证据零散，解释仍不确定。
* `INFERRED` + `confidence: high` —— 推理链很扎实，但仍未直接验证。
* `CONFLICTED` + `confidence: unknown` —— 矛盾未解，可信度无从谈起。

## 4. 各类知识的最低证据门槛

| 实体 | 才能标 `EVIDENCE_FOUND` |
|---|---|
| 程序 `PROG-` | 代码扫描结果中确有该程序，并引用到扫描输出位置 |
| 业务规则 `RULE-` | 至少 1 处直接来源（代码位置 或 文档原文）。纯推断只能 `INFERRED` |
| 数据实体 `DATA-` | 有文件/表定义来源（扫描输出或设计文档） |
| 接口 `IF-` | 有接口规格，或有生产/消费该接口的程序证据 |
| 功能 `FUNC-` | 至少 1 个实现程序 + 1 份业务描述（文档或 SME 说明）。缺一标 `INFERRED` |
| 菜单项 `MENU-` | 菜单导出中有该条目；映射到功能需**额外**证据，否则映射标 `INFERRED` |
| 批量作业 `JOB-` | 有作业清单/调度证据，或调用链证据 |
| 测试用例 `TEST-` | 有测试定义来源；执行结果另需 `raw/PRJ-####/test-results/` 引用 |
| 来源材料 `SRC-` | 材料本身在 `raw/` 中，且记录了提供方/日期/版本（未知就写未知） |

## 5. 冲突处理

1. 冲突各方**都**写进证据引用。
2. 状态标 `CONFLICTED`。
3. 正文写"冲突"段落：来源 A 说什么、来源 B 说什么、差异是什么、**谁能裁决**（哪位 SME / 哪个测试 / 哪个环境）。
4. 已确认条目被影响时：**新增**一个冲突条目并互相引用，不改已确认的那条。

## 6. 绝不能编造的东西

* 来源路径、行号、页码、工作表 / 行号
* 程序名、文件名、字段名、接口名（没实际看到就不能写）
* 测试结果——没有 `raw/PRJ-####/test-results/` 引用就不能写"通过"
* SME 确认——`reviewed_by` 只能由人填写
* 业务意图——"业务想要什么"来自人或文档，不是读代码读出来的

证据不足就写"未知"，并在待解问题里写清**要拿到什么才能确定**。

## 7. 覆盖率必须如实说明

部分材料 ≠ 全系统清单。任何分析结论都要写明覆盖范围：

```markdown
覆盖范围：本次分析了 2026-09 扫描输出中的 12 个程序，其中 9 个完成功能映射，
3 个因缺少调用上下文标为 NEEDS_REVIEW。未覆盖：批处理作业清单（尚未提供）。
```

不得从部分输入暗示已建立完整清单。

## 8. 可追溯链（目标形态）

```text
raw/PRJ-####/code-scan-results/... ──▶ PROG-0003 ──▶ RULE-0012 ──▶ FUNC-0001 ──▶ REQ-0002（未来）
                                                              │
                                                              └─▶ FS-0004 ──▶ TD-0002 ──▶ MT-0009（未来）
                                                                     └──▶ TEST-0015 ──▶ raw/PRJ-####/test-results/...
```

链条上每一环都是 ID 或路径引用。缺哪一环就是待解问题，不能糊过去。

## 9. 可复现性

* 行为可能随环境不同而变时，记录环境/版本（库、程序版本、数据环境、运行日期）。
* 行号只对被引用的**那一个文件版本**有效。`raw/` 来了新版本 → **另存新文件**，不要覆盖旧的，并更新受影响的引用。

## 10. W2/W3 的任务内核验

本节是自动修正、缺口合并与核验复用的统一规则。由 Agent 在当前任务中执行，
没有后台调度、自动评分服务或自动晋升。结构校验脚本不判断业务语义。
记录使用[分析报告模板](../analysis/reports/README.md)，演练见[合成案例](../tests/agent-evals/README.md)。

### 10.0 默认执行顺序与维护责任

以下由 Agent 在任务内完成，不让用户另写参考答案、填清单、计算摘要或选择历史报告：

1. **先找记录。** 用交付/版本/环境、实体 ID 或程序名、来源路径检索 `analysis/reports/`，核对报告正文范围；
   不能只按文件名或最新日期选择。同一分析任务续写原报告，W2 转 W3 沿用它；没有适用报告才新建。
   检索必须包含被 Git 忽略的本地报告，例如 `rg --no-ignore -l -g '*.md' -e '<实际交付或实体标识>' analysis/reports/`；
   默认 `rg` 或只查已跟踪文件会漏掉这些历史。
   其他报告中匹配的缺口用“报告路径 + 局部标记”引用原记录，保留动作历史，不复制一套待办。
2. **再分析与修正。** 从已授权的材料、交付清单和来源登记表确定发现边界及依赖；边界要能发现新增文件，
   不能只列旧引用。范围不明则声明实际可查范围，继续有证据的部分。执行 §10.1，保留未解条件。
3. **比较与复核。** 用工具生成清单与摘要，按 §10.3 判断能否复用；同一报告记录实际检查和变化，
   不要求另抄候选、另建通知表或为每个对象写一份核验文件。完整摘要可放折叠块，未变时引用原记录。
4. **更新缺口后再交付。** 按 §10.2 核对旧动作与本次剩余缺口，只提出本次确需人处理的新动作，
   提供修正结果与简短摘要，然后进入现有评审。

本地报告默认被 Git 忽略，跨机器或清理后不能保证恢复历史。找不到记录或摘要无法可靠生成时，
Agent 直接重新检查可访问材料，注明不可复用的原因；不要求用户修复缓存或补写记录。
通知历史另查可访问报告和当前会话；仍找不到就写“历史未知”，不能声称从未问过、已经解决或已获批准。

### 10.1 双向检查与自动修正

先声明任务范围及材料版本，再从来源整理必需项（条件、结果、边界、例外、关系、版本及缺口）。
从**输出回查来源**找误读和无据断言，从**来源必需项检查输出**找遗漏。
Agent 起草的必需项清单也可能漏项；未经独立核对时明确写“Agent 自检”，不据此声明完整覆盖或业务准确率。

| 发现 | 当前任务内的处理 |
|---|---|
| 误读、遗漏，且适用证据明确一致 | 修正分析草稿或提议 diff，补足引用；复核受影响的结论及关联项 |
| ID、别名、引用错误 | 查登记表和实际材料后修正；只有唯一匹配时才自动替换 |
| 无依据的确定性断言 | 撤回断言，写明未知与所需证据；不能只降低 confidence 后继续当事实使用 |
| 来源矛盾、实体身份或适用版本不明 | 保留各方证据及各自范围，标 `CONFLICTED` 或 `NEEDS_REVIEW`；不自动选边 |
| 新证据影响已确认知识 | 保留原文，生成有证据的提议变更，按 W10 评审；不静默覆盖 |

保留最小的“问题 → 来源 → 修正前后 → 复核结果”记录。无需保存完整对话。
`raw/` 始终只读。没有新增证据或可验证的修正依据时停止重试，留下具体缺口；
不得通过删除必需项、降低门槛或反复改写参考答案使结果看起来通过。
正确保留未知不算编错，但对应任务仍可能未完成；未核验项单列，不计作已核验。

### 10.2 合并缺口，避免重复询问

只有**共同缺失证据已明确、适用范围与版本相容、同一个补证动作可以解决**时才合并。
仅措辞相似或疑似同源不够；不同交付、环境、版本的同名材料不能据名称合并。
合并的是补证动作，保留每个受影响实体、证据位置、差异和知识状态。
报告内用局部标记追踪同一缺口，不分配新的业务 ID。

每组记录：缺失证据或冲突双方、适用范围、受影响对象、对当前交付的影响、最小补证动作、
上次已提出的动作及应答、重新检查条件。能从现有材料消除的问题先自行解决。

* 阻塞当前核心结论、且需要人提供材料或裁决：一次给出证据、影响和具体动作，不逐对象提问。
* 不阻塞当前交付或目前没有可执行补证动作：记录未知，继续有证据的部分，不产生额外确认请求。
* 重查后所缺证据、适用范围、所需动作及影响未变，且旧记录显示已提出、用户未要求再问：不重复询问；摘要仍说明相关部分未完成。
* 新证据、适用范围、影响或用户决定变化时重新检查；新增重大风险不能因“已问过”被隐藏。

**核验失效不等于需要再问人。** 新材料或核验口径变化后先自行重查；无关变化不能触发旧补证动作重发。
补证到达后逐对象更新：已满足的条件不再列为当前缺口，仍缺的对象和条件保留；记录解决依据，
不能整组自动关闭或把材料核对升级为 SME 确认。只有实际向用户提出过动作，才记“已提出”；草稿中的建议不算。

不重复询问不代表缺口关闭，也不代表用户同意。真实冲突仍按第 5 节保留并指定所需裁决角色；
不知道具体负责人就写角色待确定，不编造确认人。

### 10.3 核验记录与复用边界

在同一份分析报告维护记录，至少绑定以下内容；由工具计算 SHA-256，不凭文件名、日期或记忆认定未变：

1. **任务范围及发现边界**：要回答什么、适用交付/版本/环境；本次允许检索的目录或来源索引、排除范围。
2. **输入快照**：发现边界内的材料清单及每个文件的内容摘要；相关登记表、术语和知识依赖的摘要。
   记录缺失/不可访问来源。再次执行时重新枚举该边界，比较新增、删除、内容变化，不能只重查旧引用。
3. **候选快照**：被核验正文或提议 diff 的内容摘要及抽取边界。报告模板默认取 `<!-- candidate:start -->` 与
   `<!-- candidate:end -->` 之间的正文（不含标记行）；任务范围另记摘要。核验记录、记录日期及动作历史在边界外，避免自引用与无效重查。
   已有独立候选或 diff 时直接引用并注明边界，无须再复制。
4. **核验口径**：本节及适用任务要求的版本/内容摘要、核验者与方式、检查日期、实际检查项及结果。

| 比较结果 | 动作 |
|---|---|
| 范围、输入、候选及核验口径一致，旧记录有可核对的执行证据 | 复用已完成的检查，注明原记录；未检查项和未解缺口继续保留 |
| 相关文件、候选、依赖、范围或核验口径改变 | 重新核验受影响部分；无法定位影响时重查本次范围 |
| 新增材料，原引用文件未变 | 先使旧的整体核验结论失效，读取获准的新材料并检查反证；证明无关后才可复用未受影响部分 |
| 记录缺失、来源不可访问、快照无法核实或新增材料尚未读完 | 不沿用旧“通过”；重查可核验部分，其余标明未核验 |

发现边界之外的资料不在覆盖承诺内；收到外部新证据或新交付提示后，需要扩展范围重新核验。
内容摘要只证明输入相同，不证明结论正确。旧自检只能复用为自检，不能变成独立评审或 `SME_CONFIRMED`。
复用记录是先前检查的证据，业务结论仍引用原始材料。保留原发现与修订历史，不覆盖旧结果冒充首次就正确。

### 10.4 日常交付与评审

正文摘要只需说明：完成/未完成范围、自动修正、复用依据、合并缺口及本次必须处理的阻塞。
详细核验记录留在同一报告；默认本地保存，需共享时沿用现有显式留档规则。
本节不改变 W10：已知事实错误需修正或移出候选，核心冲突与必要证据缺失的部分继续留在分析层，
不能以平均分、复用记录或无人反馈代替评审。`SME_CONFIRMED` 仍只由人依据具名专家确认填写。
