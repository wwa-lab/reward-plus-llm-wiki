# 证据与验证模型

## 1. 什么是证据

证据 = 一个**人能打开并核对**的指针，指向仓库里的材料。没有证据的结论只是意见，只能放 `analysis/`。

### 引用格式

```markdown
- 来源：`raw/PRJ-0001/code-scan-results/program-inventory-2026-09.csv`，行 142 —— 程序清单
- 来源：`raw/PRJ-0001/business-documents/points-spec-v3.pdf`，第 14 页 —— 兑换规则章节
- 来源：`raw/PRJ-0001/test-cases/redemption-cases.xlsx`，工作表 Cases，第 42 行
- 来源：`raw/PRJ-0001/test-results/run-2026-09-30.log`，行 880-915
- 来源：`raw/_shared/fe-menus/menu-export-2026-08.xlsx`，工作表 MENU —— 跨 project 的通用导出
- 来源：`knowledge/programs/PROG-0003-XXX.md` —— **派生**页面，仅代表先前分析结论
```

`raw/` 下材料的路径形态是 `raw/PRJ-####/<类型>/<文件>`；跨 project 的通用材料写成
`raw/_shared/<类型>/<文件>`。**引用里必须带 `PRJ-####` 或 `_shared`**——只写 `raw/<类型>/` 无法定位到具体一批材料。

可用的定位键：行号（`行 120-168`）、页码、工作表 + 行号、程序名、用例编号、章节。

**能拿多细就写多细；拿不到就写"位置未知"。** 编造行号比不写行号危害大得多。

引用派生页面（知识页）时必须注明"派生"——它是**先前分析的证据**，不是系统行为的证据。

### 引用写在哪：两处都写，各有用途

| 位置 | 形态 | 谁在读 | 校验 |
|---|---|---|---|
| front matter 的 `source_refs` | 路径列表（YAML） | 机器 | `scripts/validate_repo.py` **会检查路径是否存在** |
| 正文的"证据与来源引用"段 | 代码路径 + 定位键 | 人 | 不校验（但 markdown 链接形态会被查） |

两处都要写。只写正文 → 机器查不到，路径写错无人发现；只写 front matter → 人翻页时看不到这条证据支持了什么。

**演练教训（2026-10-10）**：最初只校验 markdown 链接，于是 front matter 里的 `source_refs` 路径写错、
正文写成代码路径的证据全部**静默通过**。现在 `source_refs` 的路径存在性会被校验。

### 引用"默认不提交"的材料

配置快照（`raw/*/control-files/`）按约定默认不进版本库。引用它们时：

* **照常写路径**，校验脚本会对这一类路径豁免存在性检查（只记 INFO，不报错）。
* 在正文里**注明**"配置快照，默认未提交"，让 clone 仓库的人知道为什么打不开。
* 仍然要在 `knowledge/registry/source-materials.md` 登记 `SRC-####`（含 LAN 路径）——
  否则这份材料在仓库里就彻底失去线索了。

## 2. 证据强度

| 强度 | 类型 | 说明 |
|---|---|---|
| 1（最强） | 测试执行结果 | 系统实际跑出来的行为 |
| 2 | 代码扫描结果 | 程序实际实现的逻辑 |
| 3 | 系统运行观察（屏幕、作业日志） | 看到的行为，未必能从代码复现 |
| 4 | 正式规格 / 设计文档 | 期望行为，**前提是版本是最新的** |
| 5 | 叙述性文档、手册、邮件 | 意图，通常偏旧 |
| 6 | 流程图、架构图 | 结构信息，规则层面通常不精确 |
| 7 | 由命名 / 结构推断 | 仅提示性 |
| 8（最弱） | Agent 推断 | 必须显式标为推断 |

两条推论：

* **版本优先于类型。** 五年前的规格书打不过今天的代码，但也不能自动判代码赢——记录版本差异并标 `CONFLICTED`。
* **已实现 ≠ 期望。** 代码说明"实际会发生什么"，不说明"业务想要什么"。这个落差正是 `NEEDS_REVIEW` 存在的理由。

## 3. 状态与可信度

六个状态见 [knowledge-model.md](knowledge-model.md) §5。补充字段 `confidence`（`high`/`medium`/`low`/`unknown`）表达**解释**的可信程度，与状态互不替代：

* `EVIDENCE_FOUND` + `confidence: low` —— 有直接证据，但证据零散，解释仍不确定。
* `INFERRED` + `confidence: high` —— 推理链很扎实，但仍未直接验证。
* `CONFLICTED` + `confidence: unknown` —— 矛盾未解，可信度无从谈起。

## 4. 各类知识的最低证据门槛

| 实体 | 才能标 `EVIDENCE_FOUND` |
|---|---|
| 程序 `PROG-` | 代码扫描结果中确有该程序，并引用到扫描输出位置 |
| 业务规则 `RULE-` | 至少 1 处直接来源（代码位置 或 文档原文）。纯推断只能 `INFERRED` |
| 数据实体 `DATA-` | 有文件/表定义来源（扫描输出或设计文档） |
| 接口 `IF-` | 有接口规格，或有生产/消费该接口的程序证据 |
| 功能 `FUNC-` | 至少 1 个实现程序 + 1 份业务描述（文档或 SME 说明）。缺一标 `INFERRED` |
| 菜单项 `MENU-` | 菜单导出中有该条目；映射到功能需**额外**证据，否则映射标 `INFERRED` |
| 批量作业 `JOB-` | 有作业清单/调度证据，或调用链证据 |
| 测试用例 `TEST-` | 有测试定义来源；执行结果另需 `raw/PRJ-####/test-results/` 引用 |
| 来源材料 `SRC-` | 材料本身在 `raw/` 中，且记录了提供方/日期/版本（未知就写未知） |

## 5. 冲突处理

1. 冲突各方**都**写进证据引用。
2. 状态标 `CONFLICTED`。
3. 正文写"冲突"段落：来源 A 说什么、来源 B 说什么、差异是什么、**谁能裁决**（哪位 SME / 哪个测试 / 哪个环境）。
4. 已确认条目被影响时：**新增**一个冲突条目并互相引用，不改已确认的那条。

## 6. 绝不能编造的东西

* 来源路径、行号、页码、工作表 / 行号
* 程序名、文件名、字段名、接口名（没实际看到就不能写）
* 测试结果——没有 `raw/PRJ-####/test-results/` 引用就不能写"通过"
* SME 确认——`reviewed_by` 只能由人填写
* 业务意图——"业务想要什么"来自人或文档，不是读代码读出来的

证据不足就写"未知"，并在待解问题里写清**要拿到什么才能确定**。

## 7. 覆盖率必须如实说明

部分材料 ≠ 全系统清单。任何分析结论都要写明覆盖范围：

```markdown
覆盖范围：本次分析了 2026-09 扫描输出中的 12 个程序，其中 9 个完成功能映射，
3 个因缺少调用上下文标为 NEEDS_REVIEW。未覆盖：批处理作业清单（尚未提供）。
```

不得从部分输入暗示已建立完整清单。

## 8. 可追溯链（目标形态）

```text
raw/PRJ-####/code-scan-results/... ──▶ PROG-0003 ──▶ RULE-0012 ──▶ FUNC-0001 ──▶ REQ-0002（未来）
                                                              │
                                                              └─▶ FS-0004 ──▶ TD-0002 ──▶ MT-0009（未来）
                                                                     └──▶ TEST-0015 ──▶ raw/PRJ-####/test-results/...
```

链条上每一环都是 ID 或路径引用。缺哪一环就是待解问题，不能糊过去。

## 9. 可复现性

* 行为可能随环境不同而变时，记录环境/版本（库、程序版本、数据环境、运行日期）。
* 行号只对被引用的**那一个文件版本**有效。`raw/` 来了新版本 → **另存新文件**，不要覆盖旧的，并更新受影响的引用。
