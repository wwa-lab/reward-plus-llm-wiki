# reward-plus-llm-wiki

> Reward Plus 信用卡积分系统的知识库：用 AI Agent 逐步把 IBM i / AS400 遗留系统"读懂"，为迁移到 Java 平台做准备。
>
> 仓库地址：<https://github.com/wwa-lab/reward-plus-llm-wiki>

---

## 7.1 项目概述

### 这个仓库是什么

`reward-plus-llm-wiki` 是 Reward Plus 信用卡积分系统的**知识仓库**，不是代码仓库。

它把散落在代码扫描结果、业务文档、前端菜单、测试用例里的信息，整理成**有稳定 ID、有证据出处、有评审状态**的知识页面，让工程师和 AI Agent 都能追溯"这句话是从哪里来的"。

### 为什么要有它

遗留系统的知识通常有三种形态：在某个老员工的脑子里、在某份没人打开的 PPT 里、在某段没人敢改的 RPG 代码里。三种都不可靠。

这个仓库要做的是：把这三种形态**沉淀成可追溯的结构化知识**，在大规模迁移开始之前先把地基打牢。迁移一个没人说得清的系统，是迁移失败最常见的原因。

### 与源码仓库的区别

| | 源码仓库 | 本仓库 |
|---|---|---|
| 内容 | IBM i / AS400 源代码 | 代码扫描**结果**、业务文档、知识页面 |
| 是否拷贝完整源码 | — | **不拷贝**。只保存公司政策允许的扫描输出 |
| 组织方式 | 按程序/库/源文件 | 按业务功能、程序、规则、数据、接口等知识维度 |
| 回答的问题 | 代码怎么写 | 系统做什么、为什么、依赖关系是什么、迁移要动哪里 |

`raw/PRJ-####/code-scan-results/` 只放**经批准的扫描输出**（程序清单、调用关系、数据访问摘要、规则抽取结果等），不放完整源码。

`raw/` **一级按 project（`PRJ-####`）分，project 内按材料类型分**——因为材料在现实中就存在 LAN folder 里，而迁移也是按 project 走的。

两个例外：`raw/_types/` 放各材料类型的**处理规则**（规则不是材料），`raw/_shared/` 放**跨 project 的通用材料**（全量扫描、通用术语表、平台级配置）。

### 现在还不能做什么

明确说明，避免误解：

* **没有**自动摄取、自动解析、自动入库的流程——全部靠人工 + Agent 手动推进。
* **没有**接入任何代码扫描 Skill、MCP 服务或 RAG 平台。
* **没有**数据库、向量库、图数据库、Web 应用，也不引入第三方依赖。
* **没有**任何 Reward Plus 的真实业务内容——注册表是空的，这是刻意的。编造内容填充仓库会污染整个证据链。
* **没有**自动提交或自动推送。所有 commit 都是人的决定。

## 7.2 快速开始

新成员按这个顺序做一遍就够了：

1. **克隆或打开仓库**
   ```bash
   git clone https://github.com/wwa-lab/reward-plus-llm-wiki.git
   ```

2. **先确认数据处理政策，再导入材料**
   内部材料进入 Git 之前，必须确认是否允许存放。这一步不能跳。详见 [CONTRIBUTING.md](CONTRIBUTING.md)。

3. **先定 project，再把材料放进 `raw/`**
   `raw/` 先按 project 分（`PRJ-####`），再按材料类型分。例如 `raw/PRJ-0001/code-scan-results/`、
   `raw/PRJ-0001/business-documents/`、`raw/PRJ-0001/fe-menus/`；跨 project 的通用材料放 `raw/_shared/<类型>/`。
   各类型的处理规则见 `raw/_types/`。
   文件放进去后**不要再修改**，需要转换版本请放 `analysis/`。

4. **用 Cursor 打开仓库**
   Agent 会自动读到 [AGENTS.md](AGENTS.md) 和 [agents/README.md](agents/README.md) 里的操作规则。

5. **让 Cursor Agent 先读新材料和已有知识**
   直接复制 [7.9 的提示词](#79-可直接复制的-agent-提示词)，把新文件路径填进去。

6. **证据不足时，先落在 `analysis/`**
   中间结论、候选映射、冲突清单都放 `analysis/reports/`。这里的内容**不是**正式知识。

7. **评审证据、状态、冲突、ID 和内部链接**
   重点查四件事：有没有来源？结论是事实还是推理？有没有和别的来源冲突？ID 有没有重复或误用？

8. **评审通过后再更新 `knowledge/`**
   从 [templates/](templates/) 复制对应模板，填 ID、填证据引用，登记进 `knowledge/registry/`。

9. **检查 Git diff 后提交**
   ```bash
   git diff
   git status
   ```
   确认没有敏感信息、没有误改 `raw/`、没有半成品，再 commit。**不要**让 Agent 自动提交。

> **关键认知：往 `raw/` 里放一个文件，不代表它变成了已验证的知识。**
> 材料只是材料。知识是评审过的、有证据的、进了 `knowledge/` 的结论。

## 7.3 日常使用场景

### 场景 A：来了一份新的业务 PPT 或 PDF

1. 先确认它属于哪次交付 → 存到 `raw/PRJ-####/business-documents/`，文件名带上版本和日期，例如 `points-redemption-spec-v3-2026-09.pdf`。跨项目的通用文档（术语表、总体业务说明）放 `raw/_shared/business-documents/`。
2. 复制 7.9 提示词，让 Agent 输出：文档结构、涉及的业务范围、功能、规则、接口、**业务术语与领域概念**、以及文档中**没说清楚**的问题。
3. 初步结论存到 `analysis/reports/`，标注哪些是文档原文、哪些是 Agent 推断。
4. 拿它和 `knowledge/registry/` 里已有的 ID 对照：是新增实体，还是已有实体的别名？
5. 文档里的业务术语登记到 `knowledge/registry/terms.md`（`TERM-####`）；需要展开的概念建 `CONCEPT-####`。
   **术语必须指向对应的 `DATA-` / `RULE-` / `FUNC-`**，否则 Agent 用不上。
6. 评审后，才创建或更新 `knowledge/` 下的页面。
7. 页面里必须保留来源引用（文件路径 + 页码/章节），不能只写结论。
8. 如果文档说法和代码证据冲突 → 记 `CONFLICTED`，两边都留，写清谁能裁决。

### 场景 B：来了新的代码扫描结果

1. 只放**经批准**的扫描输出到 `raw/PRJ-####/code-scan-results/`。全量扫描（不属于某次交付）放 `raw/_shared/code-scan-results/`。
2. 让 Agent 输出：程序清单与职责、调用关系（callers/callees）、数据访问（读哪些文件/表）、可作为业务规则证据的代码片段位置。
3. 若扫描结果含**完整字段定义导出** → 存到 `raw/PRJ-####/data-dictionary/`（登记 `SRC-####`）。
   知识页用 `dictionary_ref` 引用它，**只写驱动行为的字段**，不要把字段清单抄进 `DATA-` 页。
4. 若扫描结果暴露了**控制文件 / 参数文件**（程序读取的参数表、数据区、硬编码常量）→ 登记 `CFG-####`。
   先判定是"真配置"还是"业务数据表"；真配置要写**反向映射（改它影响哪些程序、哪些规则）**。
   实际值放 `raw/PRJ-####/control-files/`（敏感，默认不提交）。
5. 和已有的 `knowledge/programs/`、`knowledge/functions/` 对照，标出：新增、一致、冲突、缺失映射。
6. 把"缺失映射"和"冲突"写成报告放 `analysis/reports/`，不要直接改知识页。
7. 评审后再更新知识页。
8. **不要把完整源码拷进本仓库。** 如果扫描结果里含源码、凭证、個人资料或生产数据 → 不要提交，标记待评审（见 7.7）。

### 场景 C：来了前端菜单清单

1. 存到 `raw/PRJ-####/fe-menus/`。
2. 让 Agent 梳理菜单层级和导航项，输出 `MENU-0001` 之类的候选条目。
3. **只在有证据支持时才映射到功能和程序**——菜单项与程序**不是**一对一关系，一个菜单可能触发一串程序，一个程序也可能被多个菜单调用。
4. 把握不准的映射记为 `INFERRED` 或 `NEEDS_REVIEW`，不要为了让表格好看硬填。
5. 输出"未匹配菜单项"清单，这是很有价值的缺口报告。

### 场景 D：来了测试用例和测试结果

1. 测试定义放 `raw/PRJ-####/test-cases/`，执行结果放 `raw/PRJ-####/test-results/`，两者分开。
2. 让 Agent 抽取：业务场景、前置条件、输入、步骤、预期结果、实际结果。
3. 关联到功能（`FUNC-`）、程序（`PROG-`）、规则（`RULE-`）。
4. 标出缺口：哪些规则没有任何测试覆盖、哪些预期结果和文档/代码不一致。
5. **不要因为测试通过就认定行为正确。** 测试通过只说明"这个用例的输入下是这个输出"，不等于业务需求被正确实现。

### 场景 E：要对某个规则或功能做影响分析

1. 确定目标实体：功能 / 规则 / 程序 / 数据实体 / 接口 / 外部系统 / 控制参数，拿到它的 ID。
2. 沿 `knowledge/registry/` 和知识页里记录的关系做追踪。
3. **分两栏输出**：有直接证据的依赖关系 / 推断出来的依赖关系。不要混在一起。
4. 列出可能受影响的接口、测试、菜单、批量作业、下游功能、**控制参数（`CFG-####`）**，以及**需要通知的外部系统（`SYS-####`）**。
5. **明确写出证据缺口和覆盖不完整的地方**。部分扫描 ≠ 全系统清单，不能暗示已经完整。
6. 输出放 `analysis/reports/`，标注分析覆盖范围（例如"仅覆盖了 12 个已扫描程序中的 9 个"）。

### 场景 F：按 project 导入一批交付材料（最常见的情形）

现实是：系统有很多功能，每年按 feature 给这些功能加东西，**每个 feature 就是一个 project**，
材料大多在 LAN folder 里，迁移也打算按 project 走。所以这是最常走的一条路。

1. **先认 project。** 查 `knowledge/registry/projects.md`：已有对应 `PRJ-####` 就用；没有就登记一行
   （`PRJ-####` + 名称 + 年份 + 改动类型 + LAN 位置）。**`PRJ-` 是稳定 ID，名字不是**——名字会变、会重名。
2. **把这个 project 的材料归到一处** `raw/PRJ-####/<类型>/`，只建用到的类型子目录，
   写一份 `_MANIFEST.md`（谁给的、什么时候、范围、LAN 来源）。
3. **先登记、后入库。** 材料不能进库（含源码、凭证、生产数据）→ 只登记 `SRC-####` + LAN 路径，标"待评审"。
   `source-materials.md` 里 `SRC-` ↔ LAN 路径 ↔ `PRJ-` 的对应关系就是全部线索。
4. **让 Agent 只在这个 project 的范围内抽取**，产出的每条结论都要带上 `PRJ-####`，说明"这是哪次交付引入的"。
5. **判断改动范围**：这次交付碰了哪些 `FUNC-` / `PROG-` / `RULE-` / `DATA-` / `CFG-` / `IF-`？
   在 `knowledge/projects/` 下建 `PRJ-####` 页，写清业务意图、改动清单、影响面。
6. **更新功能页的"涉及项目"**，让"这个功能被哪些交付改过"可查——行密度高的功能就是迁移风险高的功能。
7. **不要按 project 复制知识页。** 知识页描述的是系统的**当前结构**，一个功能只有一个页面；
   project 是它上面的一层时间标注，不是新的目录层级。

> **`PRJ-` 是遗留系统里已经发生过的交付，不是迁移任务。** 迁移任务在 Phase 3 用 `MT-`，
> 一个 `PRJ-` 可能拆成多个 `MT-`，一个 `MT-` 也可能横跨多个 `PRJ-`。

## 7.4 目录指南

| 目录 | 用途 | 放什么 | 不放什么 |
|---|---|---|---|
| `raw/` | 原始输入与批准的扫描输出 | **先按 project 分**（`raw/PRJ-####/<类型>/`）：扫描结果、业务文档、菜单导出、测试用例、测试结果、图表截图、**完整数据字典**、**配置快照** | 修改后的文件、完整源码、凭证、生产数据 |
| `raw/_types/` | 各类型材料的**处理规则**（不是材料本身） | 每种材料类型的规则说明 | 材料本身 |
| `raw/_shared/` | 跨 project / 全局的材料 | 全量扫描、通用业务文档、平台级配置 | 属于某次交付的材料（→ `raw/PRJ-####/`） |
| `knowledge/` | 已评审、可复用、可追溯的知识 | 功能页、程序页、规则页、数据/接口页、外部系统页、领域概念页、控制参数页、项目页、菜单页、批量作业页、架构页 | 无来源的结论、重复副本、**完整字段清单**、**生产配置值** |
| `knowledge/registry/` | 稳定 ID、规范名、别名、关系的登记表 | 各实体类型的登记表 | 业务内容本身 |
| `knowledge/domain/` | 业务语义层：领域概念（"是什么"） | 概念页 `CONCEPT-####` | 术语（→ `registry/terms.md`）、物理字段、业务规则 |
| `knowledge/configuration/` | 可调配置（"系统被怎么调"） | 控制参数页 `CFG-####`：参数项、反向映射、迁移影响 | 生产环境的具体值（→ `raw/PRJ-####/control-files/`，敏感） |
| `knowledge/projects/` | 时间轴：每次交付改了什么 | 项目页 `PRJ-####`：业务意图、改动清单、影响面 | 迁移任务（→ Phase 3 的 `MT-`）、按 project 复制的知识页 |
| `analysis/` | 中间分析与报告，**非权威** | 初步评估、候选映射、冲突报告、覆盖率报告 | 已确认为准的知识 |
| `requirements/` | 未来的需求与设计工作 | 业务需求、功能规格、Java 设计、迁移任务（**规划中**） | 遗留系统的现状描述 |
| `templates/` | 各类知识页的标准格式 | 模板文件 | 真实知识页 |
| `agents/` | Agent 如何使用本仓库 | 操作规则、工作流定义 | 业务知识 |
| `scripts/` | 轻量校验与维护脚本 | `validate_repo.py` | 有第三方依赖的工具 |
| `tests/validation/` | 可复用的验证规格（`TEST-0001`） | 派生的验证用例规格 | 原始测试结果（在 `raw/PRJ-####/test-results/`） |
| `docs/` | 仓库自身的深度说明 | 知识模型、证据模型、工作流细则 | 业务内容 |

> `tests/`、`knowledge/external-systems/`、`knowledge/domain/`、`knowledge/configuration/`、
> `knowledge/projects/`、`raw/_types/`、`raw/_shared/` 不在初始结构清单里，是按需补充的小扩展。
> 材料类型里的 `data-dictionary/`、`control-files/` 同样是按需补充的类型（规则见 `raw/_types/`）。
> 分层规则不变：原始材料仍在 `raw/`，派生知识仍在 `knowledge/`。

### 数据流向

```text
raw/  ──▶  analysis/  ──▶  knowledge/  ──▶  requirements/  ──▶  tests/validation/
 输入        中间结论        已评审知识       未来设计           行为验证
             （临时草稿）      （权威）        （规划中）
```

只有 `knowledge/` 是权威层。`analysis/` 的内容随时可以推翻重写；`knowledge/` 的变更要评审。

**`PRJ-` 横跨整条链路**：它是 `raw/` 的一级目录维度（`raw/PRJ-####/<类型>/`），也是 `knowledge/projects/` 里的时间轴，
回答"这次改动是谁带来的、动了哪些东西"。它不改变分层规则，只是给每一层加一个时间坐标。

## 7.5 知识可信度与评审规则

每个知识条目都要标状态。六个状态：

| 状态 | 含义 | 谁能标 |
|---|---|---|
| `EVIDENCE_FOUND` | 有直接证据支持（扫描结果、文档原文、测试结果） | Agent 或人 |
| `INFERRED` | 推理得出的结论，尚未直接验证 | Agent 或人 |
| `NEEDS_REVIEW` | 证据不足或需要专家评审 | Agent 或人 |
| `SME_CONFIRMED` | 相关领域专家**明确确认过** | **只能是人**，且必须记录确认人与日期 |
| `CONFLICTED` | 现有来源互相矛盾 | Agent 或人 |
| `SUPERSEDED` | 已被更新、更权威的版本取代 | Agent 或人 |

规则：

* **Agent 生成的内容不是权威结论。** Agent 可以标 `EVIDENCE_FOUND`（附来源）、`INFERRED`、`NEEDS_REVIEW`、`CONFLICTED`，但**永远不能**标 `SME_CONFIRMED`。
* `SME_CONFIRMED` 必须同时记录确认人和日期，否则不算。
* 存在冲突时：**保留冲突证据并说明问题**，不要静默覆盖先前的结论。冲突本身是有价值的知识。
* 被取代的条目标记 `SUPERSEDED` 并指向新条目，**不要删除**——我们曾相信过什么，也是追溯链的一部分。
* 可选补充字段 `confidence`（`high`/`medium`/`low`/`unknown`）用来表达解释的可信程度，与上面六个状态互不替代。

* ⬜ 新旧系统行为对比验证

对应四个阶段（方向性规划，本次不实现）：

| 阶段 | 目标 |
|---|---|
| Phase 1 知识地基 | 收集材料、规范化各类知识、维护 ID 与证据、识别冲突与缺口 |
| Phase 2 关系与覆盖 | 程序↔功能↔规则、菜单↔功能、数据↔程序↔接口、规则↔测试；覆盖率与影响分析 |
| Phase 3 需求与设计 | 抽取需求、生成功能规格、Java 技术设计与 API/数据契约、迁移依赖与任务边界 |
| Phase 4 增量迁移与验证 | 小粒度可评审的迁移任务、新旧行为对比、未解决差异与迁移风险跟踪 |

## 7.7 常见问题与处理

| 问题 | 处理方式 |
|---|---|
| **同一个功能有多个叫法** | 选一个规范名，其他全部记进登记表的 `别名` 列；多个叫法都指向同一个 ID。不要建两个页面。 |
| **某个程序没有确认的业务映射** | 状态标 `NEEDS_REVIEW` 或 `INFERRED`，写进"未匹配程序"清单。不要臆测一个功能硬塞给它。 |
| **业务文档和代码证据矛盾** | 标 `CONFLICTED`，两个来源都写进证据引用，在"冲突"段落说明差异**以及谁能裁决**（哪位 SME、哪个测试、哪个环境）。不要选一边删另一边。 |
| **Agent 给了结论但没给来源** | 退回。要求补来源；补不上就把状态降为 `INFERRED` 或 `NEEDS_REVIEW`，或移到 `analysis/`。没有来源的结论不进 `knowledge/`。 |
| **源文件里含受限信息** | 不要提交。从 `raw/` 移除或保持未跟踪，记录"已标记待评审"，并在评审结论出来前不引用它。**`.gitignore` 不是安全控制手段**，它只是兜底。 |
| **知识页过时了** | 标 `SUPERSEDED` 并指向新页面，保留旧内容。发现已确认的内容有误时，同样走"新增 + 标记取代"，不静默改写。 |
| **测试结果关联不到已知功能** | 先在 `analysis/reports/` 记录为"未关联测试"，保留其业务场景描述；等对应功能页建立后再回填 ID。不要为了关联而瞎猜。 |
| **材料不知道属于哪个 project** | 放 `raw/_shared/<类型>/`，在 `_MANIFEST.md` 里写明"归属待定"的理由，`SRC-` 备注里同步标记。**不要为了归档方便随便塞进一个 project**——归属错了会让迁移批次的范围判断出错，比不归属更糟。 |
| **同一个功能被多次交付改过** | 功能页只保留**一份**当前描述，历次改动记在"涉及项目"字段里指向各个 `PRJ-####`。不要为每次交付建一份功能页副本——那样会有 N 份互相矛盾的"当前状态"。 |
| **拿不准某个 `PRJ-` 该拆还是该合** | 按"是否一次可独立验收、可独立回退的交付"来分。拆太细 → `PRJ-` 失去批次意义；合太粗 → 一次交付里混了不相关的改动，迁移时无法分批。拿不准就标 `NEEDS_REVIEW`，请人判定。 |

## 7.8 维护流程

最简单、能长期坚持的流程，就七步：

```text
添加输入 → 分析 → 检查证据 → 评审 → 更新知识 → 校验链接与 ID → 提交
   raw/     analysis/            knowledge/        scripts/         git
```

每步的完成标准：

| 步骤 | 完成标准 |
|---|---|
| 添加输入 | 材料在正确的 project 目录（`raw/PRJ-####/<类型>/` 或 `raw/_shared/<类型>/`），`PRJ-` 归属明确，未被修改，已确认合规 |
| 分析 | 中间结论在 `analysis/reports/`，事实与推理分开标注 |
| 检查证据 | 每条结论有来源路径（+ 页码/行号/用例号），无编造 |
| 评审 | 人看过，状态已更新；`SME_CONFIRMED` 有确认人与日期 |
| 更新知识 | 用了模板、ID 已登记、无重复页面 |
| 校验链接与 ID | `python3 scripts/validate_repo.py` 无 ERROR |
| 提交 | `git diff` 已检查，无敏感信息，无半成品 |

## 7.9 可直接复制的 Agent 提示词

新材料进来时，把下面这段复制到 Cursor Agent（把 `<新文件路径>`、`<PRJ-#### 或"待判定">` 换成实际值）：

```text
你是 Reward Plus 遗留系统知识库的协助 Agent。请先阅读仓库根目录下的 README.md、
AGENTS.md、CONTRIBUTING.md 和 agents/README.md，严格按其中的规则工作。

本次新增材料：<新文件路径>
所属交付 project：<PRJ-#### 或"待判定">

请按以下要求执行：

1. 检查新增材料，并阅读仓库的操作说明与目录规则，确认材料类型（代码扫描结果 /
   业务文档 / 前端菜单 / 测试用例 / 测试结果 / 图表 / 数据字典 / 配置快照）。涉及系统间交换时，按
   knowledge/data-and-interfaces/README.md 的边界规则区分：内部程序调用记在 PROG- 页，
   用户菜单走 MENU-，只有与外部系统的交换才建 IF- 并引用对端 SYS-。遇到业务术语先查
   knowledge/registry/terms.md，新词登记 TERM- 并指向相关 DATA-/RULE-/FUNC-；完整字段定义
   放 raw/PRJ-####/data-dictionary/，不要抄进知识页。遇到控制文件 / 参数文件：先判定是"真配置"还是
   "业务数据表"，真配置建 CFG- 并写反向映射，实际值放 raw/PRJ-####/control-files/（敏感，默认不提交）。
2. 确认材料属于哪一次交付（PRJ-）：查 knowledge/registry/projects.md，已有对应项目就复用其 ID；
   没有就先提议一个新 PRJ- 并说明判定依据。材料跨 project 或全局的，归 raw/_shared/ 并注明
   "归属待定"。**不确定归属时不要随便塞进一个 project**——写进待解问题，交人判定。
3. 识别材料的来源信息：提供方、日期、版本、适用范围。来源不明就写明"来源未知"，
   不要猜测。
4. 检索 knowledge/registry/ 下的登记表和已有知识页，确认是否已存在相同实体。
   存在则复用其 ID，不要新建重复条目。
5. 抽取事实时必须附证据引用：raw/PRJ-####/<类型>/ 下的文件路径，加上页码、章节、程序名、
   代码位置、行号或用例编号（能拿到多细就写多细）。拿不到就写"位置未知"。
6. 严格区分四类内容并分开输出：
   - 事实（有直接证据）
   - 推断（推理得出，未直接验证）
   - 冲突（与现有来源矛盾，说明矛盾点）
   - 未解问题（材料里没说清楚的）
7. 需要评审的内容先保存到 analysis/reports/ 下的报告文件，不要直接写进 knowledge/。
8. 若要更新 knowledge/，请以"提议变更"的形式给出具体 diff 或新增内容，不要静默
   替换已有的权威内容，尤其不要改写状态为 SME_CONFIRMED 或已确认的条目。
9. 尽量复用已有 ID 和名称。发现多个名称指向同一实体时，记为别名并提示可能存在
   命名不一致；发现疑似重复 ID 时立即提出。
10. 每条抽取出的结论都要能回答"这是哪次交付引入的"——把 PRJ-#### 填进相关页面的
    "涉及项目"字段。**不要按 project 复制知识页**：知识页描述系统的当前结构，
    一个实体只有一个页面，project 是它上面的一层时间标注。
11. 检查内部链接是否有效、ID 是否登记、命名是否符合规范
    （FUNC-0001 / PROG-0001 / RULE-0001 / DATA-0001 / IF-0001 / SYS-0001 /
     TERM-0001 / CONCEPT-0001 / CFG-0001 / MENU-0001 / JOB-0001 / PRJ-0001 /
     TEST-0001 / SRC-0001）。
12. 最后输出变更摘要：新增/修改了哪些文件、登记了哪些 ID、哪些标为
    NEEDS_REVIEW、哪些存在冲突、还有哪些待评审任务。
13. 只有在明确记录了确认人和日期的情况下才能使用 SME_CONFIRMED；宁可标
    NEEDS_REVIEW，也不要假称专家已确认。
14. 不要执行 git commit、git push 或任何对外发布操作；不要修改 raw/ 下的原始文件；
    不要把凭证、令牌、生产数据、個人资料或未经批准的源码写入任何文件。

如果证据不足以支撑某个结论，直接说明"证据不足，需评审"，不要补全或臆测。
```
