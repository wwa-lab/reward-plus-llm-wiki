# agents/ — Agent 如何使用本仓库

给 OpenCode、GitHub Copilot 等 Agent 看的操作说明。人也要看——这是 Agent 行为的契约，评审时按它检查。

配合阅读：[../AGENTS.md](../AGENTS.md)（硬性规则摘要）、[../CONTRIBUTING.md](../CONTRIBUTING.md)（命名与 ID）、[../docs/workflows.md](../docs/workflows.md)（分步流程）。

## W2/W3 的默认执行入口

用户要求分析扫描结果、整理程序关系或抽取业务规则时，即进入 W2/W3；不要求用户说出工作流编号、
复制根 README 的提示词或另说“请做评测”。Agent 在分析前读取[任务内核验规则](../docs/evidence-and-validation.md#10-w2w3-的任务内核验)，
先找已有报告和缺口，再完成分析、修正及交付前复核。记录与内容摘要由 Agent 维护，具体顺序见该规则 §10.0。
这是当前任务内的默认行为；W10 的人工评审权限不变。

## 仓库定位

`reward-plus-llm-wiki` 是 Reward Plus（信用卡积分系统，IBM i / AS400）的**知识仓库**，服务于未来的 Java 迁移。
**源码不在这里**，这里只有经批准的代码扫描输出、业务文档、菜单导出、测试用例和从中整理出的知识页。

## 十条规则

### 规则 1：先查再建

创建任何知识页之前，先检索 `knowledge/registry/` 各表和已有知识页。
同一实体就**更新**旧页面，不新建。发现疑似重复 → 保留数字小的 ID，另一个标 `SUPERSEDED`，**不删除**。

### 规则 2：证据必须可追溯

尽量给出：`raw/PRJ-####/<类型>/` 路径 + 页码 / 行号 / 工作表+行号 / 程序名 / 用例号。
每条结论还要能回答"这是哪次交付（`PRJ-`）引入的"。
**绝不编造**来源路径、行号、程序关系、测试结果。拿不到就写"位置未知"。

### 规则 3：事实与推断分开

用状态明确区分：`EVIDENCE_FOUND`（有直接证据）/ `INFERRED`（推理未验证）。
没有依据的假设要**点名标出**，不能混在事实里。

### 规则 4：保留冲突

业务文档、扫描结果、测试结果互相矛盾时：**记录冲突 + 说明需要评审什么**。
不静默选边，不覆盖先前结论。冲突本身是有效知识。

### 规则 5：保护原始材料

不改写 `raw/` 下任何文件（不改内容、不转编码、不重命名、不删除、**不在 project 目录之间搬动**）。
不确定归属哪个 project 的材料 → 放 `raw/_shared/` 并报告，**不要为了归档方便随便塞进一个 project**。
规范化后的内容写进 `analysis/` 或 `knowledge/`。

### 规则 6：不得假称 SME 确认

只有在**记录了确认人和日期**时才用 `SME_CONFIRMED`。
Agent **永远不能**自己标 `SME_CONFIRMED`。不确定就 `NEEDS_REVIEW`。

### 规则 7：小步增量

改最小的文件集。不要基于不完整证据批量生成大量低价值页面。
一次跑通一条完整链路，好过一次铺开二十页没人看的内容。

### 规则 8：评审后才进权威层

证据有歧义或冲突 → 放 `analysis/reports/`，以"提议变更"形式给出。
不直接改写 `knowledge/` 里已确认或 `SME_CONFIRMED` 的内容。

### 规则 9：如实说明覆盖范围

只分析了一部分就写明"覆盖了 X 个中的 Y 个，未覆盖 Z"。
**不得**从部分输入暗示已建立完整的系统清单。

### 规则 10：不泄露敏感信息

凭证、令牌、连接串、生產数据、個人资料、未经批准的源码：
不写入文档、示例、报告，也不进 Git 历史。发现材料含受限内容 → 不提交，标记待评审。

## 目录归属速查

| 内容 | 目录 |
|---|---|
| 原始材料、批准的扫描输出 | `raw/PRJ-####/<类型>/`（**只读**）；跨 project 的放 `raw/_shared/<类型>/` |
| 材料类型的处理规则 | `raw/_types/`（规则说明，不是材料） |
| 中间分析、候选映射、冲突/覆盖率报告 | `analysis/reports/` |
| 已评审知识页 | `knowledge/<类别>/` |
| 交付改动范围与影响面 | `knowledge/projects/`（`PRJ-####`） |
| ID 与关系登记表 | `knowledge/registry/` |
| 可复用验证规格 | `tests/validation/` |
| 未来需求与设计 | `requirements/`（规划中） |

**判断不了放哪 → 放 `analysis/`。**

## 状态词表（只能用这六个）

`EVIDENCE_FOUND` · `INFERRED` · `NEEDS_REVIEW` · `SME_CONFIRMED`（只能人标）· `CONFLICTED` · `SUPERSEDED`

可选补充字段 `confidence`：`high` / `medium` / `low` / `unknown`。

## ID 规范

`FUNC-0001` 功能 · `PROG-0001` 程序 · `RULE-0001` 规则 · `DATA-0001` 数据实体 · `IF-0001` 接口 · `SYS-0001` 外部系统 ·
`TERM-0001` 业务术语 · `CONCEPT-0001` 领域概念 · `CFG-0001` 控制参数 ·
`MENU-0001` 菜单项 · `JOB-0001` 批量作业 · `PRJ-0001` 迁移项目（遗留交付）· `TEST-0001` 测试用例 · `SRC-0001` 来源材料

4 位数字，从登记表当前最大值 +1 分配；**永不复用、永不重排**；作废标 `SUPERSEDED` 并指向新 ID。
Phase 3 预留：`REQ-####`（业务需求）、`FS-####`（功能规格）、`TD-####`（Java 设计）、`MT-####`（迁移任务）。

**`PRJ-` 是时间轴**（哪一次交付改了什么），其余前缀是结构轴（系统当前长什么样）。
`PRJ-` 记的是遗留系统里**已经发生**的交付，**不是迁移任务**——迁移任务用 `MT-`。

## 禁止事项

* 不执行 `git commit` / `git push` / 任何发布操作。
* 不修改、移动、删除 `raw/` 下的文件。
* 不静默替换已确认或 `SME_CONFIRMED` 的内容。
* 不引入第三方依赖、数据库、向量库、图库、Web 应用。
* **不声明未实现的自动化能力**——本仓库没有摄取流水线、没有扫描 Skill 集成、没有 MCP 服务、没有 RAG 平台。
* 不批量打印 `raw/` 的完整内容到对话里。

## 完成时要报告

1. 新增/修改了哪些文件（完整路径）
2. 登记了哪些 ID
3. 哪些标了 `INFERRED` / `NEEDS_REVIEW`
4. 发现了哪些冲突，谁能裁决
5. **覆盖范围**（分析了多少、总共多少）
6. 哪些事因为证据不足而**没做**
7. 建议的下一步最小动作
8. 涉及材料导入时：材料归到哪个 `PRJ-####`（或 `_shared/`），判定依据是什么

报告模板见 [../docs/workflows.md](../docs/workflows.md) 末尾。

## 现阶段没有的东西（不要假装存在）

* 没有已安装的可执行 Agent Skill
* 没有配置 MCP 服务器
* 没有 hooks 或自动化触发
* 没有摄取/解析流水线

`agents/workflows/` 里只会放**工作流定义文档**，描述"应该怎么做"，不放可执行代码。
