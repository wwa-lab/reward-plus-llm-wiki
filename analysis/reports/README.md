# analysis/reports/ — 分析报告

`analysis/` 下专门放**成文报告**的子目录。随手笔记可以直接放 `analysis/`，成形的报告放这里。

## 常见报告类型

| 报告 | 内容 | 触发时机 |
|---|---|---|
| 代码扫描初步评估 | 程序清单、职责、调用关系、数据访问、规则候选 | 新扫描结果到达 |
| 文档分析 | 结构、业务范围、功能、规则、接口、未说清的问题 | 新业务文档到达 |
| 映射候选 | 程序 ↔ 功能 / 菜单 ↔ 功能的候选对应及依据 | 菜单或扫描材料到达 |
| 重复检测 | 疑似同一实体的多个名称或多个 ID | 登记新 ID 时 |
| 缺失证据报告 | 哪些结论没有来源、缺什么 | 定期 |
| 来源冲突报告 | 冲突双方、差异、谁能裁决 | 发现冲突时 |
| 知识覆盖率报告 | 已覆盖多少、未覆盖什么 | 定期 |
| 影响分析 | 目标实体的依赖（有证据 / 推断分列）、缺口 | 规则或功能要变更时 |

## 每份报告都要有

1. **输入**：用了哪些 `raw/` 材料（路径 + 版本/日期）
2. **覆盖范围**：分析了 X 个中的 Y 个；未覆盖 Z
3. **结论分三类列**：有直接证据 / 推断 / 冲突
4. **缺口**：按共同补证动作合并，保留受影响对象、范围与状态；说明当前阻塞及重新检查条件
5. **建议动作**：哪些可以晋升到 `knowledge/`，哪些还要等

## 报告模板（精简版）

W2/W3 由 Agent 按[§10.0](../../docs/evidence-and-validation.md#100-默认执行顺序与维护责任)检索并续写适用报告，
填写以下记录；用户无需维护清单或摘要。候选区包含结论、当前缺口与建议动作，动作历史和核验记录放在区外。
无内容的表写“无”；同一缺口跨报告引用原记录，不另造一份。

- 日期：YYYY-MM-DD

<!-- candidate:start -->

- 任务范围摘要：<上述范围和任务要求的 SHA-256>

核验规则只维护在[证据与验证模型 §10](../../docs/evidence-and-validation.md#10-w2w3-的任务内核验)。
以上为按需填写的同一份报告，不另建待办库；历史记录可复用但必须核实输入与候选版本。
原始材料仍只读，合并缺口不得抹掉来源差异；原发现、修正和未解问题继续可追溯。

## 注意

* 报告里的结论**不是**知识。引用报告时要注明"来自分析报告，未经评审"。
* 报告可以互相矛盾——那是分析过程中的正常现象，晋升到 `knowledge/` 时才需要收敛。
* 报告默认不进 Git（见 `../README.md` 的"提交策略"）。需要共享时用 `git add -f`。
