# analysis/ — 中间分析（非权威）

草稿区。在这里可以随便推翻、重写、丢弃。

## 与 `knowledge/` 的本质区别

| | `analysis/` | `knowledge/` |
|---|---|---|
| 是否权威 | **否**，随时可推翻 | 是，变更需评审 |
| 是否可作为结论引用 | **不可以** | 可以 |
| 是否需要 ID / 模板 | 不需要 | 必须 |
| 是否需要证据 | 不强求（但要记录缺口） | 必须 |
| 谁可以写 | 人、Agent 都可以 | Agent 只能提议 |

**"Agent 在 `analysis/` 里写了报告"不等于"这件事被确认了"。** 报告里写"程序 A 属于功能 X"，那还是候选结论。

## 放什么

* 代码扫描初步评估
* 业务文档分析
* 程序 → 功能映射候选
* 重复功能检测
* 缺失证据报告、来源冲突报告
* 知识覆盖率报告
* 潜在影响分析
* 读不了的材料的处理记录（尝试了什么、失败原因）

## 不放什么

* 原始材料（→ `raw/`）
* 已评审通过的知识（→ `knowledge/`）
* 任何被当成最终结论的东西

## 晋升条件

`analysis/` 里的结论要进 `knowledge/`，必须同时满足：

1. **ID 已登记**在 `knowledge/registry/`；
2. **使用了模板**，段落齐全；
3. **每条结论有来源引用**（路径 + 定位）；
4. **核心论断没有未解冲突**（有冲突就标 `CONFLICTED` 并记录，而不是先晋升再解决）；
5. **经过人评审**（状态推进与 `reviewed_by` 由人填写）。

**什么时候该留在 `analysis/`：**

* 只是一批候选映射，还没核对；
* 覆盖不完整、只分析了一部分；
* 存在冲突还没裁决；
* 只是过程性笔记，没有结论价值。

## 命名建议

```text
2026-10-09-code-scan-first-pass.md
2026-10-09-program-function-mapping-candidates.md
2026-10-09-conflicts-scan-vs-spec.md
2026-10-09-coverage-report.md
```

日期开头，方便按时间回溯。

## 提交策略

`analysis/` 下的**报告文件内容**默认被 `.gitignore` 忽略（只保留 README），因为它们是本地工作产物。

如果某份报告值得共享（例如冲突报告需要 SME 看），用 `git add -f <文件>` 显式加入，并在 commit message 里说明为什么。这样"值得留档的报告"和"随手草稿"能分开。
