# knowledge/business-rules/ — 业务规则

规范化后的业务规则。这是迁移时最容易被漏掉、代价最大的一类知识。

## 放什么

`RULE-####-<slug>.md`，从 [templates/business-rule-template.md](../../templates/business-rule-template.md) 复制。

一条规则要讲清：

* 规则描述（一句话，无歧义）
* 业务背景
* 触发条件
* 输入与预期结果
* 例外与边界条件
* 实现它的程序
* 相关功能、数据、接口
* 证据引用
* 关联的测试用例与结果
* 冲突与待解问题

## 拆分原则

**一个页面 = 一条可独立识别的规则**（一个条件 + 一个结果）。

需要"并且"连接两个独立判断的，是两条规则，拆开。原因是：迁移时它们是独立的实现点、独立的测试点、独立的变更影响面。

## 区分"已实现"与"期望"

这是本目录最关键的要求。

| 来源 | 说明 | 证据强度 |
|---|---|---|
| 代码扫描结果 | 系统**实际**怎么做 | 高 |
| 业务文档 | 业务**期望**怎么做 | 中（且要看版本） |
| 测试结果 | 实际跑出来的行为 | 最高 |

两者不同时：

* **不要**选一个删一个。
* 状态标 `CONFLICTED`。
* 在"冲突"段落写明：文档说 X、代码做 Y、差异是什么、**谁能裁决**。
* 这条差异本身就是迁移要处理的重要问题。

## 规则

1. 至少 1 处直接来源才能标 `EVIDENCE_FOUND`；纯推断只能 `INFERRED`。
2. 不编造规则内容、阈值、边界值。文档没写、代码没扫到 → 写"未知"。
3. 规则要能被测：写清"什么输入 → 什么结果"，否则无法进 `TEST-`。
4. 关联双向维护：规则页列 `PROG-`，程序页也列 `RULE-`。
5. **列出涉及项目（`PRJ-####`）。** 一条规则被多个交付改过，说明口径反复调整过——
   这是迁移时最容易理解错的一类规则，务必在"冲突"或"待解问题"里写清。
