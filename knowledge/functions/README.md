# knowledge/functions/ — 业务功能

按**业务能力**组织知识，而不是按程序。这是看遗留系统最重要的视角：系统到底为业务做了什么。

## 放什么

用业务语言描述的功能页：`FUNC-####-<slug>.md`，从 [templates/function-template.md](../../templates/function-template.md) 复制。

一页功能要讲清：

* 业务目的与边界（做什么、不做什么）
* 触发方式 / 入口（在线交易、批量作业、接口消息、菜单操作）
* 输入与输出
* 主处理流程
* 相关程序、规则、数据、接口、菜单、批量作业、测试
* **涉及项目（`PRJ-####`）**：这个功能是被哪几次交付改出来的

## 不放什么

* 程序实现细节（→ `programs/`）
* 规则本身的完整定义（→ `business-rules/`，此处只引用 `RULE-####`）
* 无来源的功能猜测（→ `analysis/reports/`）

## 规则

1. **用业务语言写。** 如果必须提到程序名才能说清这个功能，说明还没理解透，先回 `programs/`。
2. **一个功能一页。** 别名记进登记表，不建第二页。
3. **关系是双向的**：功能页列 `PROG-0003`，程序页也要列 `FUNC-0001`。
4. **标注覆盖范围**：该功能是否已被完整理解，还是只覆盖了部分场景。
5. 至少 1 个实现程序 + 1 份业务描述（文档或 SME 说明）才能标 `EVIDENCE_FOUND`；只有一侧证据标 `INFERRED`。
6. **列出涉及项目。** 功能页只保留**一份**当前描述，历次改动记在"涉及项目"里指向各个 `PRJ-####`。
   **不要为每次交付建一份功能页副本**——那会有 N 份互相矛盾的"当前状态"。

## 常见难点

| 情况 | 处理 |
|---|---|
| 功能边界模糊 | 写清"本页包含 X，不包含 Y"，并在待解问题里记录边界争议 |
| 一个程序支撑多个功能 | 功能页各写各的，都引用该 `PROG-`；程序页列出所有相关 `FUNC-` |
| 只识别出程序，叫不出业务名 | 先建 `PROG-` 页，功能页标 `NEEDS_REVIEW` 并写明"业务名称待确认" |
| 文档说有、代码里找不到 | 两条都记，标 `CONFLICTED`，写明需要哪个环境验证 |
