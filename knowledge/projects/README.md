# knowledge/projects/ — 项目 / 变更批次

**遗留系统的一次交付**，一个 project 一页，ID 前缀 `PRJ-####`。

业务能力（`functions/`）是**横截面**：系统现在能做什么。
项目（`projects/`）是**时间轴**：这些能力是怎么一年一年叠出来的。

迁移两者都需要——**迁移按 project 切，风险按 function 看。**

## 为什么需要这一层

* **迁移的工作单元**：一个 project 碰过的 function 可能横跨多个模块，按 function 切根本切不动。
* **判断去留的依据**：老 feature 常年没人用、代码还在，是遗留系统的典型包袱。
  只有知道"这个行为是哪个 project 加的、为什么加"，才敢判断能不能砍。
* **风险评估**：一个 function 被 N 个 project 反复改过 → 迁移风险高，要重点测。

## 放什么

* 年度、交付时间、变更性质（新增 / 修改 / 废弃）
* **业务意图（为什么加）**——最重要的一段
* 变更范围：涉及哪些 `FUNC-` / `PROG-` / `RULE-` / `DATA-` / `CFG-` / `IF-`
* 材料位置（`raw/PRJ-####-<slug>/` 与 LAN 路径）
* **是否仍在使用**，以及判断依据
* 迁移影响（去留建议、批次归属、风险）——**只写判断，不写方案**

## 不放什么

* **迁移方案与任务拆解** → `requirements/`（`MT-####`，Phase 3）
* 单个功能 / 程序 / 规则的详细知识 → 各自目录（本页只引用 ID）
* 材料本身 → `raw/PRJ-####-<slug>/`

## 与相邻层的分工

| 问题 | 落在哪 |
|---|---|
| 系统现在能做什么？ | `functions/`（`FUNC-####`） |
| 这个能力是什么时候、为什么加进去的？ | 本目录（`PRJ-####`） |
| 这个 feature 还在用吗？能不能砍？ | 本页的"是否仍在使用"与"迁移影响" |
| 怎么迁？拆成哪些任务？ | `requirements/`（`MT-####`，Phase 3） |
| 材料在哪？ | `raw/PRJ-####-<slug>/` + `registry/source-materials.md` |

## 命名

```text
PRJ-0001-<project-slug>.md
```

与材料目录 `raw/PRJ-0001-<project-slug>/` **同名同 slug**，方便互相对照。

（以上仅为命名**格式**示例，不是真实记录。请勿使用臆造的项目名或 feature 名。）

## 关键要求

1. **PRJ- 是稳定 ID，名字不是。** 名字会变、会重名；ID 永不复用、永不重排。
2. **业务意图必须有出处。** 来自业务文档或 SME；自己推出来的标 `INFERRED`。
3. **一个 project 对多个 function，反之亦然。** 不要试图一对一。
4. **"仍在使用"不要凭感觉填。** 有证据才填"否"（业务确认、无菜单入口、无调用）。
5. **不要把迁移方案写进来。** 本页是遗留事实，不是目标态设计。
