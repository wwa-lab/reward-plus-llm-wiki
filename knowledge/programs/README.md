# knowledge/programs/ — 程序

程序级知识，来自**经批准的代码扫描结果**。一个程序一页，全仓库只此一份。

## 放什么

`PROG-####-<名称>.md`，从 [templates/program-template.md](../../templates/program-template.md) 复制。

一页程序要讲清：

* 程序标识（名称、类型、语言、所属库、版本/扫描日期）
* 业务职责（一句话）
* 入口与调用上下文
* 调用者（callers）与被调者（callees）
* 读/写的数据
* 使用的文件、表、接口
* 相关的业务规则与功能
* 错误处理与重要副作用
* 证据引用（扫描输出路径 + 位置）

## 不放什么

* **完整源码**（本仓库不存放源码）
* 大段源码拷贝（引用位置即可）
* 未经批准的扫描信息

## 规则

1. **一个程序一页。** 发现同名不同物（例如两个库里同名程序）→ 分别登记，在别名/备注里说明，标 `NEEDS_REVIEW`。
2. **每条结论引用扫描输出位置**（文件 + 行号/程序名）。
3. **调用关系是事实，功能归属是推断。** 扫描说"A 调用 B"是证据；"A 属于功能 X"需要额外证据，否则标 `INFERRED`。
4. **批量程序也用 `PROG-`**，作业流层面的知识用 `JOB-`（见 `batch-and-jobs/`）。
5. **未匹配的程序要留痕**：没有确认业务映射的程序照常建页，状态标 `NEEDS_REVIEW`，写进"未匹配程序"清单。
6. **列出涉及项目（`PRJ-####`）。** 被多个交付反复改过的程序是迁移热区，风险高、要重点测。

## 常见难点

| 情况 | 处理 |
|---|---|
| 程序没有业务映射 | 照常建页，状态 `NEEDS_REVIEW`，待解问题写明需要什么证据 |
| 扫描结果里程序名有缩写/变体 | 全部记为别名，指向同一 `PROG-` |
| 多批扫描结果说法不一致 | 标 `CONFLICTED`，两批都引用，注明扫描日期 |
| 程序很大、逻辑复杂 | 先写主流程 + 标 `NEEDS_REVIEW`，按需拆子流程章节，不要一次写完 |
