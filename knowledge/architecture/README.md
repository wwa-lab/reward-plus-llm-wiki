# knowledge/architecture/ — 系统级架构

跨功能、跨程序的系统性结论：组件划分、集成关系、环境上下文、约束条件。

## 放什么

* 系统整体结构与主要组件
* 与外部系统的集成关系（**整体关系图/描述**；单个对端系统的档案在 `../external-systems/`）
* 环境上下文（开发/测试/生产、库结构）
* 事务与提交边界、错误处理惯例
* 编号规则、日期/金额处理惯例
* 安全模型、权限模型
* 作业调度拓扑（总览，细节在 `batch-and-jobs/`）

## 不放什么

* 单个功能或程序的描述（→ 各自目录）
* 单个外部系统的档案（→ `../external-systems/`）
* 未来的 Java 架构设计（→ `requirements/`，且要标注为规划）
* 无出处的架构猜测

## 关键要求：区分"概念性"与"已验证"

这是本目录最重要的规矩。架构图和架构描述经常是**谁画的概念图**，不是**系统实际长这样**。

每一篇架构页必须显式标注：

```markdown
> 性质：概念性描述（未验证） / 已验证的实现
> 验证依据：<扫描输出、文档、或"尚未验证">
```

标题里也要能一眼看出来。让人误以为概念图是当前实现，会导致迁移设计建立在错误前提上。

## 规则

1. 每条结论仍然要有证据引用——架构页也不例外。
2. 图与文冲突时标 `CONFLICTED`，注明图可能已过时。
3. 一次只写一个主题（例如"事务提交边界"单独一页），不要写一本大杂烩。
4. 环境相关的结论要写明是哪个环境。
