# knowledge/domain/ — 领域知识

业务侧对"这套系统在讲什么"的共同理解。**它回答"是什么"，不回答"什么条件下怎样"**（后者是 `business-rules/`）。

## 为什么需要这一层

Agent 读代码能知道 `PTS_BAL` 是个数值字段，但不知道它指的是"可用积分"还是"累计积分"。
领域知识就是补上这个语义，并且**把业务词映射到代码事实**。缺了它，所有结论都建立在误解上。

## 放什么

* **领域概念页（`CONCEPT-####`）**：值得展开的概念。定义、边界（不包含什么）、关键口径、生命周期、与哪些 `DATA-` / `RULE-` / `FUNC-` 对应。
  ID 登记在 [`../registry/concepts.md`](../registry/concepts.md)，页面在 [`concepts/`](concepts/)。

## 不放什么

* **术语的一行定义** → `knowledge/registry/terms.md`（`TERM-####`）。本目录只放需要展开的概念。
* **业务规则** → `business-rules/`（"什么条件下怎样"）。
* **物理字段与类型** → `data-and-interfaces/`（`DATA-####`）+ `raw/PRJ-####/data-dictionary/`。
* **系统级架构与集成关系** → `architecture/`。

## 与相邻层的分工

| 问题 | 落在哪 |
|---|---|
| 这个词是什么意思？有没有别的叫法？ | `registry/terms.md`（`TERM-####`） |
| 这个概念包含什么、不包含什么、怎么流转？ | 本目录（`CONCEPT-####`） |
| 什么条件下会怎样？ | `business-rules/`（`RULE-####`） |
| 代码里对应哪个字段 / 文件？ | `data-and-interfaces/`（`DATA-####`） |
| 系统实际怎么实现的？ | `programs/`（`PROG-####`） |

## 命名

```text
CONCEPT-0001-<概念slug>.md
```

（以上仅为命名**格式**示例，不是真实记录。请勿使用臆造的业务概念名。）

## 关键要求

1. **定义必须有出处。** 来自业务文档或 SME；自己推出来的标 `INFERRED`。
2. **写清边界。** "不包含什么"往往比"包含什么"更能防止误解。
3. **指向代码事实。** 概念页要列出对应的 `DATA-` / `RULE-` / `FUNC-`，否则 Agent 用不上。
4. **概念 vs 规则不要混。** 概念是"是什么"，规则是"什么条件下怎样"。
