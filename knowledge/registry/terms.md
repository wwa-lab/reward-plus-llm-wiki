术语表是**业务侧与代码侧之间的消歧层**。同一个词在业务文档、程序、报表里往往有不同叫法，
不同业务含义也可能共用一个词。没有这一层，Agent 会把"业务说的积分"和代码里的字段当成两件事。

> **本表是唯一一例「行即记录」的登记表**（与 [source-materials.md](source-materials.md) 同理）：
> 术语不单独建知识页。一句话定义足够消歧，拆成两处只会造成不一致。

## 如何追加一行

1. 检索"规范名"与"别名"，确认尚未登记。**同一概念被叫成多个名字 → 记别名，不新建 ID。**
2. 新 ID = 当前最大 ID + 1，例如 `TERM-0001`。
3. "一句话定义"用**业务语言**，不写实现细节。写不下就说明该建 `CONCEPT-`，而不是把表撑爆。
4. "易混淆项"填**容易与它混为一谈**的术语（可写 `TERM-####` 或词）。这一列比定义更值钱。
5. "相关实体"填它落到哪些 `DATA-####` / `RULE-####` / `FUNC-####` / `IF-####` —— **这是 Agent 从业务词走到代码事实的桥。**
6. 证据引用：业务文档位置（页/章节）。定义无出处就标 `NEEDS_REVIEW`，不要自己编。
7. **更新文件头部的"当前最大 ID"**。

## 状态取值

`EVIDENCE_FOUND` · `INFERRED` · `NEEDS_REVIEW` · `SME_CONFIRMED`（需记录确认人与日期）· `CONFLICTED` · `SUPERSEDED`

## 注意

* **两个来源对同一个词的定义不一致时，不要选一个**：拆成两行或标 `CONFLICTED`，写明谁能裁决。
* 术语的"定义"是**业务认可的说法**，不是"代码实际怎么算"。后者属于 `RULE-` 或 `CONCEPT-`。
* 只登记**会引发误解或需要对齐**的词。不要把业务文档的词汇表整篇抄进来。
